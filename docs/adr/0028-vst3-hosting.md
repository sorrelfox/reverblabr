# ADR-0028: VST3 plugins through the distribution's VST3 SDK headers, 3.8 or later, with a host side of our own

- **Status:** Accepted
- **Date:** 2026-10-29

## Context

Many effects people already have on Linux are VST3® plugins: LSP and ZAM ship them beside their LV2 and CLAP builds, and the tools that bridge Windows plugins to Linux hosts mostly expose them as Linux VST3 bundles. A VST3 plugin runs in a `reverblabr-plugin-host` of its own (ADR-0014), and its own window has to fit what ADR-0025 decided for LV2 and CLAP: the same messages, the same undo, the same window.

What had to be settled first was the SDK the format is defined in, and how the build gets it.

- **Its licence.** Up to 3.7 the VST3 SDK was offered under the GPL 3.0 or Steinberg's own licence; a host built with it was GPL 3.0 as a whole. From 3.8.0 on, the SDK and each of its parts (`pluginterfaces`, `base`, `public.sdk`) is under the MIT licence: the `LICENSE.txt` of each of Steinberg's repositories on GitHub says so, for the tags `v3.8.0_build_66` and `v3.8.1_build_84` and for `master`. MIT code can be part of an MPL-2.0 program, with its copyright notice kept.
- **The name is a trademark.** "VST" is Steinberg's registered trademark. The SDK comes with usage guidelines (`VST3_Usage_Guidelines.pdf`) for the logo and the word; they are separate from the code's licence, and ask for an attribution wherever the word is used.
- **Who packages it.** Fedora 44 has the SDK 3.8.1 (`vst3sdk-devel`: the headers under `/usr/include/vst3sdk`, and the SDK's helper sources built into libraries of Fedora's own naming). Debian unstable has 3.8.0. Ubuntu 26.04 has 3.7.10 only.
- **What a host needs of it.** The format is a set of COM-like interfaces, each with a 16-byte id, declared in `pluginterfaces` as headers. The SDK's helper classes (the `FUID` objects, its hosting module loader, its stream and message classes) are sources a host may use, but none of them is needed: each interface header declares its id as a constant beside it, and what a host must offer a plugin (a host context, a component handler, a frame, a stream) is a handful of small classes.
- **Describing.** A bundle (`Name.vst3/Contents/<machine>-linux/Name.so`) built with SDK 3.7.5 or later says which classes it has in `Contents/Resources/moduleinfo.json`, without its code being run. It does not say what a plugin's settings are or how many channels it has: only the plugin's controller and component say that, once made.
- **The build fetches nothing.** The project builds from what the distribution installs; the CLAP SDK is found the same way and is optional because Ubuntu does not package it.

## Decision

**The SDK is the distribution's interface headers, 3.8 or later, and nothing else of it.** CMake looks for `pluginterfaces/vst/ivstaudioprocessor.h` (under `vst3sdk/` on Fedora and Debian) and reads the version from `vsttypes.h`. `RB_BUILD_VST3` is on when 3.8 or later is found and off otherwise; a build without it has no `plugin.vst3` block and does not look for VST3 plugins, as a build without the CLAP SDK has no CLAP block. None of the SDK's sources or libraries is compiled in or linked: the host's side of the interfaces is ours (`pluginhost/vst3module.*`, `vst3plugin.*`), and every interface is asked for by its id.

**Finding and describing.** A plugin is a bundle, a folder ending in `.vst3`, anywhere under `~/.vst3`, `/usr/local/lib64/vst3`, `/usr/local/lib/vst3`, `/usr/lib64/vst3` and `/usr/lib/vst3`, and under the folders `VST3_PATH` names, which other Linux hosts read too: those as well, not instead. What is inside a bundle is never taken for another one. Its plugins are described in the scan helper (`--scan vst3 <bundle>`), where code that crashes takes only that process: the classes are those `moduleinfo.json` lists when the bundle has one, and the factory's otherwise; a bundle whose `moduleinfo.json` lists no plugin's sound is not loaded at all; each plugin is then made, asked for its settings and channels, and let go. A plugin's id is its class id as 32 hexadecimal digits; a host is told the bundle with `--location`, as a CLAP host is told its file.

**Running.** The component and its controller (one object, or two of the classes the component names) are joined through relays of the host's, one each way, and the controller is given the component's state (unless it is empty, which some plugins cannot be given). **A relay passes a message on only when it is sent on the host's main thread**: a component that speaks from inside its process call is not heard, so the controller never runs on the audio thread, as the SDK's own hosts have it. The first main audio bus each way, wherever it is among the buses, is the block's ports; the other buses are switched off and given silence, or somewhere to write; event buses are off. Processing is started on the main thread, before the audio thread has the plugin. A mono plugin on a stereo lane runs twice, once a side, or once on the two sides mixed, as LV2 and CLAP ones do; the second instance is a component alone, given the first one's state, every change the first is given and every message the controller sends; what it says itself goes nowhere, the first instance speaking for both. **The audio thread allocates nothing**: a cycle's parameter changes, in and out, go in queues made before it starts.

**A setting is the plain value the plugin shows**, and the plugin is told the 0 to 1 it maps to. The mapping is asked of the controller once, as points along the range: one a step for a stepped parameter, which is exact, and 257 for a continuous one, between which a value is found on a straight line, or on a curve of equal ratios for a logarithmic parameter. Both threads use the same points both ways, so a value turned into 0 to 1 and back is the value. A stepped parameter is a choice when its steps have words, a switch when they are off and on, and a whole number when they are numbers. Hidden, read-only and program-change parameters are not shown; one the window moves still reaches the sound, and what the sound gives out (a meter) reaches the controller.

**State and presets are the format's own.** A block's state is both halves' states in a `.vstpreset` of its own, kept as base64. A plugin's presets are the `.vstpreset` files for its class under `~/.vst3/presets/<vendor>/<plugin>` and the system's `/usr/share/vst3/presets` and `/usr/local/share/vst3/presets`, where other hosts keep them; one saved from the block goes to the user's folder, written whole and then put in place, under a name made one file's name (no folders, no control characters, never `.` or `..`), and never over another plugin's preset or one of another name that made the same file name. Only a file in those folders is put in, links followed, and none larger than 64 MiB. A preset is put in with the audio thread kept away (`HostProcessor::hold()`).

**Its window is ADR-0025's.** The plugin's editor view is put inside the host's X11 window as `X11EmbedWindowID`. The frame the view is given resizes that window when the view asks, and is the run loop the format has a Linux view ask for: its timers and descriptors are the host's main loop's, as CLAP's timer and descriptor support are. What a person does arrives as `beginEdit`, `performEdit` and `endEdit` on the main thread: a value goes to the audio thread through the host's own queue and to the engine as ParamChanged, never back; the hold and the letting go are ParamGesture, one undo step. What the engine or the sound changes is told to the controller on the host's turn, thirty times a second. When the plugin says its values changed by themselves, they are read and given to the sound; when its latency changed, it is deactivated and activated again with the audio thread kept away, as the format asks, and the latency read then; when its buses changed, it is made again with its state, as a CLAP plugin is when it asks for a restart.

## Consequences

- `vst3sdk-devel` is a build dependency on Fedora. A Kubuntu 26.04 build has no VST3 block until Ubuntu packages 3.8 or later; a build from a 3.7 SDK is refused rather than made GPL 3.0 without anyone deciding so.
- What of the SDK ends up in the program is what its headers define inline. CREDITS.md lists the SDK with its licence, and the documentation that names VST3 carries Steinberg's attribution. **The attribution line, and no logo**: wherever a page names VST3, it carries the line "VST is a registered trademark of Steinberg Media Technologies GmbH.", and the VST logo is not shown anywhere. The README, the AppStream entry and the About page don't name VST3; the plugin formats there are named in general.
- **What one half of a plugin sends from the audio thread is dropped**, not queued for later: holding on to it would mean the plugin's own message objects travelling between threads. Plugins built on the SDK send from the main thread, as its own hosts drop the rest too.
- **Approximations**, all of them where a plugin is unusual: a value between two points of a continuous parameter is near, not exact, what the plugin makes of it; a parameter whose values turn back on themselves is shown as the plugin's own 0 to 1; a parameter change takes effect from the cycle's first sample.
- **Not offered**: a plugin's program lists (the presets some plugins keep inside themselves rather than as files), notes in or out, a side chain from another lane, and a run loop asked of the host rather than of the window's frame, which the format does not promise.
- The view is the owner's desktop check as much as a test: the tests run the tests' own plugin (`tests/vst3`), whose view is a stand-in that uses the run loop as a real one does, in a parent of the test's own (`Vst3Plugin::setViewParents`), and LSP's VST3 build where it is installed.

## Alternatives considered

- **Vendoring `pluginterfaces`** under a third-party folder. The MIT licence allows it, but it is a copy to keep up to date, and Fedora and Debian already ship the same headers.
- **Fetching a pinned SDK release during the build** (FetchContent with a hash). It would work everywhere, but a build that downloads is one distributions cannot use, and the project builds from what is installed.
- **Linking the SDK's hosting helpers** (`Module`, `PlugProvider`, `HostApplication`), as Fedora's `vst3sdk-hosting` library has them. Their library names are Fedora's own and Debian packages them differently, and they bring thread and loop assumptions of their own where the host has one main loop already; what they do for a host is a few hundred lines here.
- **SDK 3.7 or earlier.** GPL 3.0 for the whole host, which is not ours to choose in passing.
