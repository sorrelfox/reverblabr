# ADR-0026: Broadcast: our own source client, FFmpeg's encoders, TLS through GnuTLS, and the password in the desktop's secret store

- **Status:** Accepted
- **Date:** 2026-10-29, TLS added 2026-10-30

## Context

The Broadcast block sends a session to an internet radio server: Icecast 2, which most stations and every hosting service run, and SHOUTcast, whose source protocol Icecast speaks too. Listeners join a stream at any moment, so what goes out has to be something a player can start in the middle of: MP3 or AAC frames, or Ogg pages whose headers the server keeps for each new listener. The stream has to come back by itself after a server restart or a dropped network, and the title listeners see has to follow what is playing.

Four things had to be chosen: what speaks to the server, what encodes the audio, how the connection is kept private, and where the password lives.

- **The protocol is small.** An Icecast source sends one HTTP request (`PUT` since Icecast 2.4, `SOURCE` before it) with Basic authentication and the station in `Ice-` headers, and then the audio as the request's body for as long as it streams. A SHOUTcast source sends its password on a line of its own to the port after the listeners', reads `OK2`, and sends `icy-` headers. A new title is a separate `GET /admin/metadata` (Icecast) or `/admin.cgi` (SHOUTcast) request. An Ogg stream carries its title in its own comment header instead, and a new title there is a new logical stream chained onto the last.
- **The encoders are already here.** The Recorder's M4A files are made with the distribution's FFmpeg (libavformat, libavcodec), which on Fedora and Kubuntu has LAME for MP3, libopus, libvorbis and FFmpeg's own AAC encoder, and muxes MP3, ADTS and Ogg to any writer, including memory.
- **The password crosses the network with every connection**, in Basic authentication or on SHOUTcast's first line, and so does every title request. Icecast 2.4 takes sources over TLS on a listening port marked for it (often 8443), with a certificate of the server's; SHOUTcast's version 1 source protocol has no TLS at all. A source that sends a password across the internet has to be able to encrypt it, and to know that the server is the one named, before the first release.
- **The password must not be in the session file**, which people copy and send to each other. The engine runs in `reverblabrd` (ADR-0017), so whatever keeps it has to work in a process with no window. Nothing in the project used a secret store yet; ADR-0004 already names KWallet as part of the native Plasma integration.

Measured against Fedora 44's Icecast 2.4.4 in a container (tests/broadcast): `PUT` with no `Expect` header is answered `200 OK` and the audio follows; MP3, AAC and Vorbis titles set by the requests above show on the server's pages; an Opus stream's title is carried in the stream, which players show, but Icecast 2.4 neither reads Opus comments nor takes a metadata request for an Opus mount.

## Decision

- **Our own source client** (`engine/stream`), over a plain non-blocking socket: Icecast's `PUT`, falling back to `SOURCE` when a server answers `405` or `501`, and SHOUTcast's protocol. Every wait (connecting, sending, the server's answer) can be called off within 50 ms, so a session that stops never waits for a server.
- **TLS through GnuTLS, over the same non-blocking socket**, for Icecast when the block's "Secure connection (TLS)" is on (the `secure` setting; SHOUTcast is never asked for it). The handshake waits a slice at a time as everything else does, in the direction GnuTLS says it is waiting, so a server that stops answering halfway is let go of within 50 ms of the stream stopping, and gives up when the connection's time is up. The title requests go over TLS too when the stream does, since they carry the password.
  - **What is checked**: the chain up to an authority in the system's trust store (the distribution's, with any the person added), the dates, and the host's name, or its address when an address was typed; the name goes to the server as SNI unless it is an address. TLS 1.2 or later, whatever the system's crypto policy would allow, with the policy's ciphers.
  - **No switch to skip the check, and no pinned certificates for 0.1.0.** A certificate that is refused stops the stream and says which of the three is wrong (`certificateUntrusted`, `certificateExpired`, `certificateWrongHost`, or `certificateInvalid` for anything else), and is not tried again until something changes: the password is never sent to a server that could not prove who it is. A server whose certificate is its own making is a server on the person's own network, where plain TCP is what they have today, or one they run, whose certificate they can add to the system's trust store as for any other program. A pasted fingerprint would need a field, a place to keep it, and a story for the day the certificate is renewed; it is worth it once somebody needs it, not before.
  - **Why GnuTLS**: both distributions' FFmpeg already links it (`libavformat-free` on Fedora and `libavformat` on Kubuntu use it for their own https and rtmps), so the stream adds a build dependency (`gnutls-devel`, `libgnutls28-dev`) and nothing at run time. Its non-blocking mode drops onto the client's own polling: `GNUTLS_E_AGAIN` and the direction it waits in are all the loop needs. Its verification says what was wrong with a certificate as flags, which is what a status that names the reason needs.
- **FFmpeg encodes**, writing to memory: MP3 through LAME with no tag in front and no index, AAC as ADTS through FFmpeg's own encoder (never libfdk_aac, as for the M4A recordings), Opus and Vorbis through their libraries in Ogg pages half a second long. A format the system's FFmpeg cannot make is listed as unavailable in the catalogue, as the Recorder's are. The stream goes out at the session's rate when that is 44.1 or 48 kHz, at 48 kHz otherwise and always for Opus, converted on the stream's thread with the recordings' resampler.
- **The audio thread only copies.** The block writes each cycle into a ten-second tap (the Recorder's `rt::AudioTap`, ADR-0010), and a thread for each Broadcast block drains it, encodes, sends and reconnects.
- **Reconnecting backs off**: one second, doubling to a minute, shortened at random by up to a fifth; a connection that lasted ten seconds starts the count again. A refused password, no password, no host or a missing encoder stops trying until something is changed, and says so once.
- **The title** is a template (`%artist - %title` by default) filled from what is playing: a text file the block is pointed at, looked at once a second, or a track handed to the stream by anything that knows (`BroadcastStream::setNowPlaying`), which is how a media player's now-playing comes in: the engine watches the MPRIS players on the session bus (`engine/mpris`) while a block's title follows one, and hands the stream each new track, no two closer together than a second. MP3 and AAC titles go to the server's metadata request; an Ogg stream's go in a new chained stream's comment header.
- **The password lives in the desktop's secret store, through QtKeychain**, in the engine: KWallet on Plasma, the Secret Service elsewhere, under the folder "Reverblabr" and the key `broadcast/<session>/<block>`. QtKeychain's plain-text fallback is off: with no store, a password is refused, not written down. The window hands a new password to the engine once (`SetBroadcastPassword`, over the session bus, which only the user's own processes reach); the engine reads it from the store when a stream starts, keeps it in memory while the session runs, and removes a session's passwords when the session is deleted.

## Consequences

- A required build dependency for TLS, GnuTLS 3.7 or later (`gnutls-devel`, `libgnutls28-dev`), and none at run time, since the system's FFmpeg brings the library already.
- One new build dependency, QtKeychain for Qt 6 (`qtkeychain-qt6-devel`, `qtkeychain-qt6-dev`), small and in both distributions, and **optional** as RNNoise is (ADR-0016): a build without it has no Broadcast block (`RB_BUILD_BROADCAST`), since a stream with nowhere safe to keep its password is not one to offer. The package's spec asks for it by name. The protocol and the encoders add nothing; TLS adds GnuTLS's headers.
- The bit rates offered are the ones each encoder takes for the channels chosen (Vorbis from 48 kbit/s for stereo and to 192 for mono, Opus to 256 for mono); a setting outside them is streamed at the nearest one. The encoder is made before the server is asked, so settings it refuses never take a mount point, and are not tried again until they change.
- Nothing the engine waits on can hold a stopping session: the host's name is looked up on a thread that is left behind when the wait is called off, the title request has a thread of its own, and a now-playing file is read only when it is a regular file, without waiting.
- A Broadcast block taken out of a session keeps its password while an undo can bring it back; when the session is closed and its history goes, the passwords of blocks no longer in it are removed.
- **A password goes encrypted where the server offers TLS**, and in the clear to a server that does not, which the panel says next to the setting; the status says whether the connection that is up is secure (`secure`). A SHOUTcast server cannot be reached securely: its source protocol has no TLS.
- A TLS server is usually on another port than the plain one, and the block does not guess it: the port is the person's to set, as the server's operator gives it.
- A server that answers on the TLS port with something that is not TLS, or offers nothing newer than TLS 1.1, is `tlsFailed`, and not tried again until something changes.
- An Opus station on Icecast 2.4 shows no title on the server's own pages; listeners' players show it.
- Everything below the engine runs without Qt, PipeWire or a server: the unit tests stream to a server the test makes, over TLS through a TLS server with a certificate authority the test makes (a good certificate, another name, an untrusted authority, an expired one, a stalled handshake), and an integration test streams every format to a real Icecast in a container (`ctest --preset container`), and MP3 with its titles to the same Icecast's own TLS port.
- A copied or imported session has no password for its Broadcast blocks until one is set again, which is the point.

## Alternatives considered

- **libshout.** It speaks the same protocols and has TLS, but takes no part in encoding: the audio would still be FFmpeg's. It would be one more library for both distributions to package and the build to require, its blocking calls would need its non-blocking mode and our own polling anyway to stop promptly, and the title of an Ogg stream would still have to be put in the stream by us. Our client is a few hundred lines with tests against both a made-up server and a real one.
- **FFmpeg's own `icecast://` protocol.** It sends the stream, but cannot set a title on a running stream, does not speak SHOUTcast's protocol, and reports a lost connection only as a write error with no reason, which the status and the backoff need.
- **OpenSSL over the same socket.** It would do the same job as well, but neither distribution's FFmpeg links it for itself (Fedora's libavformat reaches libssl only through other libraries), so it would be a library more to rely on, for no gain over GnuTLS.
- **FFmpeg's `tls://` protocol through avio**, as Live Stream uses for RTMPS (ADR-0027). It waits through FFmpeg's interrupt callback, which FFmpeg looks at every 100 ms rather than 50, and it reports a refused certificate as an I/O error with the reason only in FFmpeg's log, so the status could not say whether the certificate was expired, for another name or from an unknown authority.
- **QtNetwork's QSslSocket.** The stream's layer is plain C++23 without Qt, tested without an event loop; QSslSocket wants one, and would bring QtNetwork and its TLS plugin into the engine for one socket.
- **A switch to accept any certificate.** It would make TLS a show of security: anybody between the block and the server could take the password. Refused by design; see above for a server with a certificate of its own.
- **libsecret or KWallet directly.** QtKeychain is the same thing behind one API, picks the store the desktop has, and is what other KDE applications use for the same job.
- **The password in the session, scrambled.** Anybody with the file has the password; a session is a file people share.
