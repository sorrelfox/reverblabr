# Architecture

Reverblabr captures, processes and routes audio on the KDE Plasma desktop. The user builds **sessions**: chains of **blocks** laid out left to right on a canvas. Sources take audio from applications, input devices or the whole system; effects and meters process and measure it; outputs send it to devices. A running session becomes a real-time processing node inside PipeWire.

This document describes how the pieces fit together and the rules that keep them working. The reasons behind the big choices are recorded as [architecture decision records](adr/README.md). Day-to-day coding rules are in [conventions.md](conventions.md).

## Goals that shape the design

- **No glitches.** Audio is processed on PipeWire's real-time thread. Nothing that runs there may wait, allocate or fail.
- **A good citizen in the user's audio graph.** Reverblabr only adds connections. It never reroutes another application's audio and leaves nothing behind when it stops or crashes.
- **An engine without a GUI.** The engine must be able to run in the background, so it depends on neither the GUI nor KDE Frameworks.
- **Native on Plasma.** The GUI uses Kirigami and follows the user's colour scheme, fonts and language.

A layer uses only the layers below it. The rules are enforced, not just written down:

- `cmake/RbLayering.cmake` walks every target's complete link closure at configure time and stops the build if a forbidden library shows up anywhere in it. Tests in `tests/cmake/` prove that the check fires.
- `reverblabr-engine` links the lower layers privately, so the GUI can't even include their headers. The facade in `engine/core` is the only way in.

The real-time, DSP and graph layers are plain C++ because their code runs on the real-time thread and must be testable offline, without an audio server. `engine/rt` sits at the bottom because every layer above it, blocks included, has something to say to or from the audio thread; see [ADR-0010](adr/0010-real-time-communication-primitives.md). The engine avoids KDE Frameworks and Qt's GUI modules because it will run as a headless background service.

## Process model

**At first, one process.** The GUI embeds the engine, which runs on its own thread behind a **facade**. The facade is shaped exactly like the future D-Bus interface: only D-Bus-compatible types, structured data as JSON strings, asynchronous calls, and errors as codes. See [ADR-0003](adr/0003-in-process-engine-behind-facade.md).

**[`dbus/io.github.reverblabr.Engine1.xml`](../dbus/io.github.reverblabr.Engine1.xml) is the source of truth**, and it is held to be: the XML is put through `qdbusxml2cpp` and the client proxy it produces is compiled, so a shape D-Bus cannot express fails at build time; and `engine.Facade.MatchesTheInterfaceDefinition` compares the XML with `rb::core::EngineFacade`'s own metaobject, method for method and argument for argument, in **both** directions (something in C++ that is not in the XML fails too, because a client reading the XML would be missing what the GUI quietly relies on). Designing to the interface from the start is what made the move to a daemon plumbing rather than redesign.

**`rb::core::Engine` answers the interface for real.** It owns the sessions on disk, the ones that are open, the runtime of each one that is running, and the connection to PipeWire they share. A session is sent to a client whole once, as a snapshot, and after that only the edits, each carrying the revision it produced; a client that sees a revision it did not expect has missed one and asks to resynchronise, which is what makes a gap visible rather than silently wrong. **Turning a knob produces no patch**: `SetParam` is too frequent to send back, and the client that turned it already knows. **An edit may arrive as a list of commands**, which is how a client says "this is one thing I did" when one thing takes more than one command to say: a link between two blocks is a wire per channel, because a link only ever joins two ports of the same channel position ([ADR-0007]), and what the person drew was one link. A list applies whole or not at all, comes back as one patch per command with the revision each produced, and is one step to take back. `rb::core::MockEngine` answers the same interface from memory, with no PipeWire anywhere, so interface work can start before the engine it talks to is finished and the tests of that interface can run on a machine with no sound card.

**Running a session is `rb::core::SessionRuntime`** (`engine/core/sessionruntime.h`). It makes a block for every block instance in the session from the registry, compiles them into a graph, gives PipeWire a node with a port for every block that takes audio from the system or hands it back, and keeps all of that true as the session is edited. The blocks that do are the capture blocks and the Output Device, which say so themselves (`BlockInfo::inputsFromAudioSystem`, `::outputsToAudioSystem`); everything between them stays inside the graph. The blocks belong to the runtime, not to the graph, which is what lets a recompile keep what they remember. A block whose type this build does not have is not dropped: the session keeps it exactly as it was so that saving cannot lose it, and the runtime says it cannot run a session containing one.

**Later, a background engine** ([ADR-0017](adr/0017-engine-daemon.md)). `reverblabrd` (`daemon/`) is the engine and nothing else (no GUI, no KDE Frameworks), serving the interface `io.github.reverblabr.Engine1` on the session bus under the name `io.github.reverblabr.Engine`, so sessions keep running when the window closes or crashes.
- **The bridge is generic** (`engine/bus`). `bus::EngineService` answers each method of the XML by calling the facade method of the same name, first letter lowered, and relays each facade signal as the D-Bus signal of that name; only the facade's own members are served. `bus::RemoteEngine` is the window's `EngineFacade`: every method sends the call, every signal is the D-Bus one re-emitted.
- **Started on demand.** A D-Bus activation file names the systemd user unit `reverblabrd.service` (`Type=dbus`); the first call starts it. Only Auto Run enables the unit (below).
- **It outlives the window, not the other way round.** It exits by itself after a minute with no client and no session running. It writes down which sessions are open (`$XDG_STATE_HOME/reverblabr/daemon.json`) and, started again after a crash, opens them again **stopped**; `--safe-mode` opens none. `RemoteEngine` watches the name, and when a new daemon has it, asks again for what it has open and every lasting answer (lists, catalogue, states, and each session's analysed block as last asked), so the window comes back by itself.
- **Auto Run** ([ADR-0021](adr/0021-auto-run.md)) is a session setting, `autoRun`: `off`, or `login`. `rb::daemon::AutoRun` (`daemon/autorun.*`) does two things with it. As the daemon starts, unless in `--safe-mode`, it opens every session set to `login` that is only on disk and starts it once it has opened, and starts one it reopened where it is, so such a session runs whenever the engine does: at login, after a crash restart, or when a window's call brings the engine up. And it keeps `reverblabrd.service` enabled exactly while any session is set to `login`, through the user service manager on the session bus (`rb::daemon::AutostartUnit`: `GetUnitFileState`, `EnableUnitFiles` or `DisableUnitFiles`, then `Reload`, as `systemctl --user enable` does): when it starts, after the setting changes, after a session opens or closes, and whenever anybody lists the sessions, which is how one deleted without being open is noticed. It reads the list through `Engine::sessionListing()`, not `listSessions()`, so looking puts nothing on the bus. A masked unit is left alone, and one not installed, or no service manager, is said in the log and nothing more. Only the daemon talks to systemd; a window running its own engine says in the Info tab that Auto Run needs the background engine.
- **Its data is the application's**: the daemon runs under the name `reverblabr`, so it keeps the same sessions, presets, recordings and plugin cache as the engine in the window.
- **Levels are mapped, not sent** ([ADR-0018](adr/0018-telemetry-in-shared-memory.md)). Every open session publishes its snapshots into a sealed memfd (`core::SharedTelemetry`). The daemon hands a window a read-only descriptor for it once, through `io.github.reverblabr.Telemetry.Share`, served beside the engine's interface. `RemoteEngine::telemetryOf()` maps it, and nothing about levels crosses the bus after that. So a window on the daemon has meters, wire colours and state dots.
- **One per desktop**. The window registers `io.github.reverblabr.reverblabr` with KDBusService in Unique mode (the organization domain is `reverblabr.github.io`, so the name is ours, not `org.kde`). A second launch hands its arguments to the first and ends before it has chosen an engine or made a window; `ui::LaunchRequests` reads them (`--new-session`, `--sessions`, `--open-session <id>` from KRunner's Open, or none) and the window acts on them, with the launch's activation token passed on through `KWindowSystem::updateStartupId()` so that Wayland lets the window come forward. `--mock` takes no name.
- **The daemon is the default.** `bus::chooseEngine()` decides once, before the window opens: `--mock`, then `--in-process`, then `--daemon` when given; otherwise `bus::reachDaemon()` asks the bus whether the name is owned, whether any activation file names it, and has the bus start it (`StartServiceByName`, up to 10 s). A window that cannot reach it runs the engine in its own process, and `engine.daemonUnreachable` (`noSessionBus`, `daemonNotInstalled`, `daemonRefused`) goes in its banner from the start and stays whichever session is in front. The in-process engine stays for the tests, `--mock` and `--in-process`. The command-line tool, `reverblabr-ctl` ([ctl.md](ctl.md)), reaches the daemon over the same bus, through the public API alone.

**Plugin hosts** ([ADR-0014](adr/0014-plugin-host-process.md)). Third-party plugins (LV2, CLAP, LADSPA and VST3) run in separate `reverblabr-plugin-host` processes, each as its own PipeWire node. A crashing plugin takes down only its host, and its block is bypassed.
- **A plugin block splits the session** into segment nodes linked through the host's node. PipeWire runs the chain in one cycle, so a host adds no latency beyond what its plugin reports.
- **The engine and a host talk over two channels.** Parameters go through a ring in shared memory, straight to the host's audio thread. Everything that owns memory goes through a socketpair.
- **`pw::PluginHostProcess` watches each host.** A pidfd shows when it exits. A heartbeat in the shared memory, standing still while the node before it runs on, shows a hang. `PR_SET_PDEATHSIG` makes sure no host outlives the engine.

### Timers

A session's timers ([the data model](#session-data-model)) start it at set times, with no window open and no engine running.

- **Firing one** is the facade's `fireTimer()` (`FireTimer` on the bus), the same in the engine and the mock: `core::TimerRunner` opens the session if it is only on disk, starts it once `SessionOpened` has gone out, and stops it once the timer's duration is over, counted from when it fired. The end is a time of day, looked at least every 30 seconds, so a machine that slept through it stops the session when it wakes. Somebody stopping the session ends the run; the engine stopping it to start it again after PipeWire or WirePlumber restarted does not. A session that was already running when the timer fired is left to whoever started it, and `TimerFired` says so (`started` false). **A fire from systemd is checked against the clock**: the unit passes `scheduled`, and one more than two minutes after the timer's last time (`core::previousRun()`), as a machine waking from sleep hands it over, is refused with `timer.late`; a fire by hand runs whenever it comes.
- **Quitting the captured applications** (`core/quitapplications.*`) goes by what the server says of each stream's client, never what the application says of itself: a client that came through the portal (`pipewire.access.portal.app_id`) is a Flatpak, ended with `flatpak kill`; any other is the process on the client's socket (`pipewire.sec.pid`). That process is held with a pidfd, checked to be this user's (the owner of `/proc/<pid>`) and to run the binary PipeWire named (its executable's or its command's name), and then sent `SIGTERM` through the pidfd, so a pid reused in between gets nothing.
- **The background engine keeps a systemd user timer for each timer that is on** (`rb::daemon::TimerSchedule`, `daemon/timerschedule.*`), so the time comes with no window open and no engine running. It writes `reverblabr-timer-<id>.timer` (`OnCalendar=` from `core::onCalendar()`, `AccuracySec=1s`, `Persistent=false`, `WantedBy=timers.target`) and the `.service` it starts (`Type=oneshot`, `ExecStart=` the `reverblabr-ctl` installed beside the daemon, `timer-fire --scheduled -- <id>`) into `$XDG_CONFIG_HOME/systemd/user` (`daemon/timerunits.*`), then has the user service manager `Reload`, `EnableUnitFiles` and `RestartUnit` the timer, as `systemctl --user daemon-reload`, `enable` and `restart` would. A timer switched off or deleted, or one whose session was deleted, is `StopUnit`'d and `DisableUnitFiles`'d, then its files go. It looks when a timer or a session's name is edited, a session opens or closes, and whenever anybody lists the sessions, through `Engine::sessionListing()` like Auto Run; only files whose first line says it wrote them are ever rewritten or removed, and a unit of one of its names that does not say so is left alone and said in the log. A timer whose unit is written but not enabled (no `timers.target.wants` link: the manager refused, or there was none) is enabled at the next look, and a refusal has it look again a minute later. A one-off whose time has passed has its units removed, fired or not. The mock daemon (`--mock`) keeps no units at all. The timer's call starts the daemon by D-Bus activation, and the daemon stays while the session runs. Units are visible with `systemctl --user list-timers 'reverblabr-timer-*'`. Waking the machine from suspend for a timer is not done: a user timer cannot set `WakeSystem=`.
- **`listTimers()`** lists every session's timers, closed ones' too, with the calendar expression each starts on and when it next runs (`core::nextRun()`).

## From session to sound

1. **Session model** (`engine/core`). A session is a set of blocks and the wires between them. The model changes only through **edit commands** (`addBlock`, `removeBlock`, `moveBlock`, `connect`, `disconnect`, `setParam`, `rename`, `setNotes`, `setEnabled`, `setSessionSetting`, `applyPreset`, `setTimer`, `removeTimer`). Each command is validated, applied, published as a numbered patch and can be inverted, which is what undo uses.
   - **Undo is a stack of gestures, not of events** (`rb::core::EditHistory`). A drag of a slider is a hundred `setParam` commands and a drag of three selected tiles is sixty `moveBlock` commands, and Ctrl+Z has to take back the drag rather than the last pixel of it, so an edit that carries on what the one before it was doing is merged into the step already there. Time is what a gesture is measured in, for want of anything better: nothing in the protocol says when a mouse button was released. The history lives in the engine, so the GUI and the CLI undo the same things in the same order, and **an undo applies its commands the way any edit is applied**, through the live-update path and out as patches, so a session that is running is heard to change.
### What a block is

Every block, whether source, effect, meter or output, implements one interface, `rb::dsp::Block` (`engine/dsp/block.h`). Its **parameter descriptors** are the single description that drives the DSP, the generic settings panel, the presets, the session file and later the D-Bus API, so a new block needs no new code in any of them.

- **`prepare(spec)` against `process(context)`** is the division that matters. `prepare()` may allocate and takes as long as it likes; `process()` may do neither and follows the [real-time rules](#real-time-rules). Everything a cycle needs is reserved in `prepare()`.
- **Parameters arrive two ways.** A number (a float, an int, a bool, or which choice of an enum is taken) reaches the audio thread through the parameter queue and `applyParam(index, value)`, and the block glides to it inside itself so the signal never steps. Text, such as a device reference, owns memory and never reaches the audio thread: changing it changes the graph and goes through a recompile.
- **A parameter the session plan reads is structural**, and the block declares that by clearing `ParamFlags::automatable`: which device to play to, which application to capture, whether alert sounds are wanted. What has to change for one of those is links and ports, so `Engine::setParam` plans the session again rather than queueing a number nothing would read, and the catalogue carries the flag so an interface knows not to stream such a value as a control moves. Everything else, such as a gain or a mute, costs a queued number and no recompile, which is what keeps a drag cheap.
- **Read-only parameters are block outputs**, such as a gain reduction or an activity light. The block writes them in `process()` and the telemetry sampler reads them. They are never saved and never set from outside.
- **Ids are stable for ever** (the block's type id, its parameter ids and an enum's choice ids), because a session file holds them. An enum is saved as its choice's id, not its position, so a later version may reorder the choices. There are no names and no descriptions in the engine at all: those are translated and belong to the interface, which keys its own table by these ids (see [i18n.md](i18n.md)).
- **State is a map of id to value** (`saveState()` / `loadState()`), with a JSON equivalent for every type. A parameter a saved state does not mention goes back to its default; an id this version does not know is ignored, so a session written by a later one still opens.
- **A side may carry more than one signal, in lanes**. `PortSpec::laneWidth` says how many consecutive ports are one signal and `laneLabels` names each (`"main"`, `"background"`); nought, the usual case, is one lane however many ports. The canvas draws a connector a lane, a link is dropped into the lane it is let go over and becomes wires into that lane's ports, and the catalogue carries both numbers. The first block with two is **Ducking** (`advanced.ducking`): a voice on `main` turns the music on `background` down, by a straight-line ramp whose attack and release are the whole way down and back at any depth, with a hold that bridges the gaps between words; out comes the two mixed, the voice untouched.
- **The Mixer** (`advanced.mixer`) is the other block with lanes: five stereo inputs, each a strip with a volume (0–200 %), a mute, an additive solo and a balance, and a master over them all. **A volume change takes the time it was asked to take.** The strip's gain moves in a straight line over the strip's *ramp*, a hidden parameter the interface sends in the same edit as the volume (the ramp, the volume, the ramp put back to a drag's 20 ms), so a fade takes 0.5 s (2 s with Shift) and a scene is recalled over 1 s, and undoing either is one step that ramps back. The change is started in `applyParam()` as it arrives rather than read at the top of a cycle, because by then the ramp has been put back. Scenes A–E are five saved sets of the five volumes, held in hidden parameters so a session and a preset keep them.
- **The Input Switch** (`advanced.inputswitch`) is the third block with lanes: A and B in, one out, with an equal-power crossfade between them. The position runs in a straight line and the gains are its cosine and sine, so two unrelated signals of the same loudness keep it all the way across. The crossfade time is sent with the switch as the Mixer's ramp is with a volume (0.5 s for a click, 2 s with Shift), and `input` is an ordinary enum parameter, so a command or a shortcut can switch it too. **An enum's choice goes through the parameter queue as its position** like any other number; before the Input Switch the runtime only wrote it into the block from the engine's thread, which reached a block that reads its store every cycle but not one that has to hear the choice in order with the numbers sent beside it.
- **One ear is a setting, not a mono lane**. The hearing blocks work on one ear each, and lanes stay stereo pairs, so such a block has the shared `ear` parameter (`dsp::earParam()`: `left` or `right`) and runs its one-channel process through `dsp::EarRouter`, which feeds it FL or FR and passes the other side through a delay line of the block's own latency; the ears stay sample-aligned, in series on one lane or side by side. A change of ear fades the processed side to the unprocessed one, switches at a cycle's edge, resets the process, waits out its latency and fades back in. `ear` is kept out of presets (`ParamFlags::inPresets`): a saved preset leaves it out and applying one never sets it, so a preset for one ear loads into the block for the other. **Join L/R** (`hearing.joinlr`) is the side-by-side layout's other half: FL from its `left` lane, FR from its `right` lane, no latency of its own, since the compiler lines the lanes up where they meet. Both sit in the **Hearing** category.
- **Moving sound from one range into another** is `dsp::FrequencyMover`, apart from its blocks because two use it: a short-time Fourier transform on `RealFft` (Hann frames a quarter frame apart, the latency one frame: 1024 samples at 48 kHz for high sound, 2048 for sound from 250 Hz up (`kMiddleFrameMs`, about 43 ms) and 4096 for lower sound, which needs about 12 Hz a bin to be told apart (`kLowFrameMs`, about 85 ms)), moving **peaks with the bins round them** rather than bins (Laroche and Dolson), each peak shifted by the distance it is carried rounded once from where it truly is, and its phase carried on at the frequency it lands on. **Harmonics** (experimental) does not move a peak but makes its harmonics in the destination: the peak read as a tone (amplitude and phase from its bin and the Hann kernel where it truly is) and each harmonic the tone's own windowed spectrum at its exact frequency, its phase the peak's times the harmonic, so it goes on from frame to frame with nothing to remember. Up to four moves, each reading the input, so their order does not matter; "when needed" compares a move's source with everything on its destination's side of it. `dsp::carriedTo()` is the map, and the panels' `FrequencyMoves.qml` repeats its arithmetic for the arrows and the map (QML tests hold them together). **Frequency Lowering** (`hearing.frequencylowering`) and **Frequency Raising** (`hearing.frequencyraising`) are one `FrequencyMoveBlock` (the mover's settings on one ear through `EarRouter`, publishing which moves acted as bits and, while its panel looks, as band values), each with a `FrequencyMoveKind`: which way it carries, its methods and defaults, its range and its frame. Raising's kind has a long frame as well, taken while a move in use (on or off) starts below 250 Hz: the block says which through `dsp::Block::preparedShape()`, and a move dragged across the line has the runtime prepare a fresh block and line the graph up with its new latency (ADR-0022). A move set the other way does not act. Their panels and faces are one `FrequencyMovePanel` and `FrequencyMoveFace` given the type; each asks for the spectra of its own ear.
- **The listening blocks' filterbank** (ADR-0019). `dsp::GammatoneBank` splits one ear into 64 gammatone channels on the ERB scale, 100 Hz to 16 kHz, and puts them back together flat and exactly 4 ms late; the gains change on a fixed 32-frame grid whatever the cycle length, so the block is block-size invariant. `dsp::BandLayout` lays a block's bands over the channels, and **reads levels per channel**: each channel's own reading, then the loudest within the band spacing, so a tone gets its band's gain in every channel it goes through. `dsp::BandGainControl` follows the levels at the block's speed and applies each band's soft, average and loud gains (at −55, −40 and −25 dBFS), Loudness, the noise floor, the most gain and the ceiling (`dsp::steadyGainDb()`). **Hearing Compensation 16** (`hearing.compensation16`) runs that through `dsp::EarRouter` and a true-peak limiter; its ceilings are on the fitting rule's listening scale, 85 dB above dBFS, so `core::fitHearingBlock()` writes them as they are. While analysed it publishes each band's gain now and then its level, for its panel's "now" line. **Hearing Compensation 64** (`hearing.compensation64`) is the same block with one band to each channel, the level coupled over ±2 ERB, and is set through up to 24 control points: `dsp::bandsFromPoints()` gives each of the four settings its own `dsp::MonotoneCurve` through the points in log frequency (Fritsch and Carlson's tangents, so the curves never overshoot the points), read at every band each cycle; `core::fitHearingBlock()` places a point at each frequency the audiogram measured. Its 64 gains and 64 levels are why `rt::kMaxBandValues` is 128.
- **`BlockRegistry`** turns a type id from a session file into a block, and lists what exists for the library sidebar. An unknown id is an error code, not a crash: the block is kept and flagged (`block.unknownType`).

2. **Graph compiler** (`engine/graph`). It turns the model into an immutable **compiled graph**:
   - It validates: a source is present (a block that captures from the system, or one with no inputs at all that makes something, like Wave; never the category a block is listed under), there are no cycles, no wire is dangling, and port limits are respected.
   - Where several wires arrive at **one input port**, it inserts a hidden unity-gain sum, because a port carries one signal. The interface draws that as one connector per lane with a second, wider ring around it, not as one dot per channel. The connector itself is a hollow ring whose border takes the live colour while its block is passing audio (read from the same value as the tile's state dot, so the two cannot disagree) and the accent while a Ctrl-drag could land on it. One per lane rather than one per channel, because the channels are how a link is carried and not something to make somebody wire up twice. One output feeding several inputs needs nothing: they all read the buffer it was written into.
   - It orders the blocks topologically, breaking ties the same way every time.
   - A **disabled block compiles to a pass-through** rather than being left out, so the ports either side of it keep their places, but only where there is something to pass through. What "off" means depends on what the block has on its edges: a block with a connector on both is in the middle of a lane and is passed through, and a block missing one is **silenced**. A capture block receives nothing from anybody, and a generator has no input to fall back on, so a source that is off cannot be the source of a sound; an output block has no downstream wire for a pass-through to feed, only the hardware. The block says which it is (`BlockInfo::inputsFromAudioSystem`, `::outputsToAudioSystem`), not the category it is listed under. **A block with several input lanes is passed through as all of them, summed**, so a ducker switched off leaves the voice and the music both playing rather than only the first lane. Fading across the change is a separate matter, and for a silenced block the fade runs to silence.
   - It preallocates every buffer for the largest possible cycle, 8192 frames, so a change of PipeWire's quantum never needs a recompile. A buffer is reused as soon as nothing still has to read it, so the pool grows with the depth of the graph rather than with the number of ports.
   - It records how much latency the signal has picked up at each block, along the longest path to it, and **lines up every path that meets**. At a merge point, which is a hidden sum or a block with more than one input (a Mixer's strips, a Ducking block's voice and music, an Input Switch's A and B), each input arrives as late as the latest one: an earlier one is copied into a buffer of its own and held back by the difference, so one sound reaching the same place two ways adds up rather than combing or cancelling. Only `BlockInfo::latencySamples` counts; a delay added on purpose is not lined up with (below). A bypassed block keeps its latency, so switching it off moves nothing.
   - **A recompile keeps what the delay lines hold.** A new graph makes new lines, and a new line is silence for as long as its delay; so when the node hands over a graph, on the audio thread between two cycles, the new graph takes over what the old one's lines hold wherever it has the same line: the same wire held back by the same amount, the same bypassed block (`CompiledGraph::carryOverFrom()`, `DelayLine::takeStateFrom()`). Without it an edit anywhere would put a gap into every held-back path.
   - **The session says how late it is.** The node reports the graph's latency as its `SPA_PARAM_ProcessLatency` whenever a graph is handed over and it has changed, and PipeWire adds it to the latency of the node's ports, which is what a recorder or a streaming tool downstream reads to line its own tracks up. The status bar shows it as "+1.5 ms processing", and a block that adds latency says so in its tile's tooltip.
   - **Block instances live outside the compiled graph**, so a block keeps its state (envelopes, filter memory) when the graph is recompiled. Preparing them is the runtime's business, not the compiler's: re-preparing on every compile would reset the state a recompile exists to preserve. So a block is prepared only when something it was prepared *for* has really changed (the rate, the layout the plan gave it, or what its settings say through `dsp::Block::preparedShape()`), and never where it stands: a block that needs preparing again is already in the live graph, and `prepare()` reallocates the buffers a cycle is reading. It is replaced instead, by a fresh block carrying its settings and prepared before it is anybody's, and the one it replaced waits with the retired instances until the graph that points at it has been swapped. A fresh block starts empty, so its lanes stay silent after the swap for as long as the new graph's latency before they fade back up (`SessionUpdate::refilled`, ADR-0022).
3. **Session processing node** (`engine/pw`). Each running session is one PipeWire filter node (`pw_filter`) named `reverblabr.<session-uuid>.seg0`, made by `rb::pw::SessionNode`. Its ports carry 32-bit float mono audio, one port per channel, named `<blockId>:<in|out>_<channel>` (for example `b1:in_FL`). A session with plugins in it is several nodes, `seg0`, `seg1` and so on (below).
   - **A plugin cuts the session into segments** ([ADR-0014](adr/0014-plugin-host-process.md)). A plugin runs in a `reverblabr-plugin-host` process as a node of its own, so the blocks either side of it cannot be in one compiled graph. `graph::splitIntoSegments()` puts each block in the segment numbered by the most plugins on any path to it, which keeps every wire running forward and a session with no plugin in it one segment, compiled from exactly the spec it always was. Each segment is a graph of its own in a node of its own, and PipeWire runs segment, host and segment in one cycle in the order their links give: measured at quanta 64, 256 and 1024 with one plugin, two in series and two side by side (`pw.plugin-sessions`).
   - **What crosses goes through a boundary block** (`graph::SegmentBoundary`), which says its audio comes from, or goes to, the audio system and passes it straight through, so the node gives it ports like any source or output and needs to know nothing about plugins. The ports are named after the boundary: `<block>.send` for a block's sound leaving for a later segment, `<block>.recv<N>` for it arriving in segment N, and `<block>.feed` for a plugin's inputs leaving for its host. The link manager is told the links between them, and to each host's node by its name, so a host that is not there yet is linked when it comes.
   - **A plugin's inputs meet in a graph first.** All of them are gathered in one segment and leave together, never straight from one host to another, so latency compensation can line them up; and an arriving boundary carries the latency the sound picked up before it, so the graph of a later segment holds a path around a plugin back by exactly what the plugin reported. Each node tells PipeWire only its own share of the latency, and the status bar adds up the longest path through them all.
   - **A plugin's own window and presets are its host's** ([ADR-0025](adr/0025-plugin-windows.md)). The engine asks for them over the control socket (OpenUi, ListPresets and the rest); a value moved in the window reaches the plugin in the host and comes to the engine as a message, which the block and the session take without sending it back, and every client hears as a patch. A gesture the plugin reports is one undo step however long it took; the values a person's preset leads to are one step too.
   - **The plugin block (`blocks::PluginBlock`) is what stays in the engine**: which plugin, its state as the host last gave it, the latency the host reported, and the plugin's parameters. A knob on it goes to the host's audio thread through the shared ring rather than to a graph; saving asks the host for its state; a host that becomes ready gets that state back, or the parameter values. A plugin that is switched off is not hosted at all and passes the sound through, like any block that is off.
   - **A plugin that goes down is linked around**.
     - **Noticed:** a host's exit comes through its pidfd, measured at 6 ms from the kill to the sound coming back. A host that stops running is noticed by its heartbeat standing still while the segment feeding it runs on, for three cycles and 40 ms, measured at 54 ms. A heartbeat still for a whole second counts as a hang on its own, because a host stopped while PipeWire changes the graph can hold everything still, the segment before it too.
     - **The bypass:** what went into the host goes from the segment before it straight to the segment after it. The link manager reconciles at once rather than after its settling time.
     - **After it:** a host that stopped is killed. Its latency comes off the paths beside it. The block publishes what its host is doing, and the engine reports `plugin.crashed` or `plugin.stoppedResponding`, which puts a badge on the tile.
     - **Starting it again:** a host that had run for ten seconds is started again by itself; one that fails sooner waits for Restart (`RestartPlugin`). A restarted plugin gets back its last state, then every value set since, which the host holds back until the state is in, so none of them reaches the plugin being replaced.
   - **An "unknown resource" error from PipeWire is about one object, not the connection.** Letting go of a link to a host that had just been killed used to tear the whole connection down, and every session with it.
   - **Installed plugins are found by the plugin host, never in the engine**.
     - **Finding candidates is safe in the engine.** Each format (`plugin::PluginFormat`) says where its plugins live and which entries there are candidates: an LV2 bundle, a CLAP file, a LADSPA library. Finding them means reading names, never loading anything.
     - **Describing them is not**, so each candidate is described by a `reverblabr-plugin-host --scan <format> <path>` of its own, four at a time. A candidate that crashes takes only that process with it. It is blocklisted and the scan goes on. **The time limit is on progress, not on the whole**: the host writes each plugin's line as soon as it is described, and a candidate is given up on only after ten seconds with no new line. One that had told of no plugin by then is blocklisted as hung; one that had is *incomplete*: what it told is kept, with what an earlier scan found in it that this one did not reach, the block library says some plugins may be missing, and the next scan looks into it again. LSP's CLAP file, 194 plugins, takes about a second on an idle machine and took over nine under a parallel build; a limit on the whole had cut it off and blocklisted it with nothing found.
     - **What was found is kept** in `plugins.sqlite` in the user's cache, with each candidate's modification time. A scan describes only what is new or has changed, forgets what has gone, and retries a blocklisted candidate only when asked. LSP's 27 LV2 bundles, 194 plugins, take about a second the first time and nothing after.
     - **The engine scans the first time it is asked** (`ListPlugins`) and when a folder it looks in changes.
     - **Every plugin is an entry of its own** in the library, under Plugins, for a format this build can host. The entry is a key, `plugin.<format>?plugin=<id>`, carried where a block's type is, and `SessionModel::addBlock()` reads it back into one block set to that plugin.
     - **A new format is a `PluginFormat`, a describer in the host and a loader.** The scan, the cache and the library need nothing more.
   - **A plugin's choice is its value as the scan wrote it** (`%.9g`), in the block and in the panel alike, and a new host is given a choice from the file as its position, as it is given a number.
   - **LV2 plugins run in the host through lilv**.
     - **The ports:** audio, control and atom. An atom input gets a sequence written afresh each cycle, holding what the plugin's window said to it; what the plugin says on an atom output goes to the window while one is open.
     - **The features:** the URID map and unmap.
     - **The plugin's settings are its control inputs, in port order**, which the scan describes (symbol, name, range, default, and whether it is a number, a whole number, on or off, or one of its scale points). So the engine builds a `plugin.lv2` block's parameters from the cache without loading the plugin, and the host numbers the ring's changes the same way. A choice travels as its position among the scale points and becomes the value in the host.
     - **The state is lilv's**, as Turtle: the controls, and whatever the plugin keeps through the state extension. That is what the session file holds for it.
     - **The latency is the plugin's latency port**, read as it runs and told to the engine when it moves.
     - **A mono plugin on a stereo lane** runs twice, once a side (the default), or once on the sides mixed, with a mono output on both sides.
     - **Settings a machine cannot describe**, for a plugin it hasn't got or hasn't scanned yet, are kept and saved again as the file had them.
     - **The plugin's own window** ([ADR-0025](adr/0025-plugin-windows.md)) is loaded through suil in the host: a UI that shows itself, or an X11 UI put inside an X11 window the host makes (`pluginhost/x11window`), XWayland's on a Wayland desktop, where it was last for that plugin. A control the window moves goes to the audio thread through a queue of the host's own and to the engine as ParamChanged, and `ui:touch` arrives as ParamGesture; the window is told every control that differs from what it last heard, thirty times a second.
     - **Its presets are LV2's** (`pset:Preset`), listed and put in through lilv, the audio thread held away from the plugin while the state goes in, and saved as a bundle in `~/.lv2`, where other LV2 hosts find them.
   - **LADSPA plugins run in the host through dlopen()**. The format's few structures are declared in `plugin/ladspaabi.h`, so building it needs no SDK.
     - **A plugin is its library's file name and its label**, `amp.so:amp_stereo`, found in the folders `LADSPA_PATH` names or the usual ones. The file name and not the path, so a session moves between machines that keep plugins in different folders. The library ends at the first `.so:`, because some labels (LSP's) are URLs.
     - **The settings are the control inputs, in port order**, each named by its port's name made into an id (`Frequency (Hz)` is `frequency_hz`; a second port of one name gets `_2`). The range hints give the range, the kind (on or off, whole numbers) and the default; bounds given as a fraction of the rate are described at 48 kHz, and an open end of a range is given one, up to twice a numeric default.
     - **The state is the control values**, which is all a LADSPA plugin has. **The latency** is a control output called `latency`, by the format's convention. A plugin that cannot write its output over its input gets a copy of it when the two would be one buffer.
     - **A mono plugin on a stereo lane** runs as an LV2 one does. LADSPA has no windows, so the panel built from the settings is the plugin's only face.
   - **CLAP plugins run in the host through the CLAP SDK**, where the build has it (`RB_BUILD_CLAP`; Kubuntu 26.04 does not package it, and the build then has no `plugin.clap` block and looks for no CLAP plugins).
     - **Found:** `.clap` files anywhere under `~/.clap` and the system's CLAP folders, and under the folders `CLAP_PATH` names, which add to those rather than replacing them, as the CLAP specification says.
     - **Described by loading them**, which is the only way CLAP says what a plugin is. Each plugin in the file is made, asked and let go once the next is made: LSP's 194 share a worker thread that takes 50 ms to stop, and the file took 6.5 s to describe when each was let go first, 1.35 s now. What plugins print goes to standard error, not into the lines the engine reads.
     - **The plugin's settings are its parameters** that are neither hidden nor read-only, by the plugin's own numbers for them. CLAP says only that a parameter is stepped, so what the steps are comes from the words the plugin gives its values: numbers, off and on, or a choice at each place the words change, found by halving (LSP steps its choices through fractions of 0 to 1).
     - **A CLAP id does not say which file it is in**, so a host is started with `--location`, where the scan found the plugin.
     - **A change is an event** at the start of the next process call, and a value the plugin reports back is taken as what the setting is. A choice travels as its position, as for LV2.
     - **The state is the plugin's own**, through the state extension, kept in the session as base64. A restart the plugin asks for is the plugin made again with its state, as for a new rate; its latency is read then.
     - **A mono plugin on a stereo lane** runs twice or on the sides mixed, as for LV2.
     - **The plugin's own window is the `gui` extension's** ([ADR-0025](adr/0025-plugin-windows.md)): put inside an X11 window the host makes when there is a display and the plugin can be, where it was last for that plugin; otherwise floating, as the plugin's own X11 window, or a Wayland one where it offers that on a Wayland desktop. The host answers its requests to be resized, shown, hidden and closed. **Its main thread is the host's PipeWire main loop**, through the `timer-support` and `posix-fd-support` host extensions; a timer or a descriptor asked for while the plugin is being made is watched once there is a loop.
     - **What the window moves arrives as output events**: the first instance's values, with `PARAM_GESTURE_BEGIN` and `END` round them, go to the main thread through a queue, and on to the engine as ParamChanged and ParamGesture; a mono plugin run twice has the other instance hear them in the next cycle. A value the host sent and the plugin says back is no news, and is not passed on. `params.rescan(VALUES)` has the host read every value again and tell the engine.
     - **Its presets are its own**, found through its preset-discovery factory (a file location is walked for the file types its provider declared) and put in through `preset-load`; it says when one is in, and its values follow. **One kept from a CLAP block is ours**, in our preset folder: the plugin's id, its state and every setting, listed only for blocks of that plugin.
   - **VST3 plugins run in the host through the VST3 SDK's interface headers**, 3.8 or later, where the build has them (`RB_BUILD_VST3`, [ADR-0028](adr/0028-vst3-hosting.md); Kubuntu 26.04 packages only 3.7, and the build then has no `plugin.vst3` block and looks for no VST3 plugins). None of the SDK's sources is compiled in: the host's side of the interfaces is its own (`pluginhost/vst3module.*`).
     - **Found:** bundles, folders ending in `.vst3`, anywhere under `~/.vst3` and the system's VST3 folders, and under the folders `VST3_PATH` names, which add to those. Nothing inside a bundle is taken for another one.
     - **Described** in the scan helper: the classes a bundle's `moduleinfo.json` lists, or its factory's when it has none; a bundle whose `moduleinfo.json` lists no plugin's sound is not loaded. Each plugin is then made, its settings and channels asked, and let go once the next is made, as for CLAP: LSP's 194 take about 1.3 s.
     - **A plugin is its class id**, 32 hexadecimal digits, and its host is started with `--location`, the bundle.
     - **Its two halves**, the component and the controller, are joined through two relays of the host's, which pass a message on only when it is sent on the main thread, so the controller never runs on the audio thread. The controller is given the component's state. The first main audio bus each way is the block's ports; any other bus is switched off and hears silence.
     - **A setting is the plain value the plugin shows.** The plugin is told the 0 to 1 it maps to, found from points along the range asked of the controller once: one a step for a stepped parameter, 257 for a continuous one, on a curve of equal ratios for a logarithmic one. A stepped parameter is a choice, a switch or a whole number by the words of its steps. Hidden, read-only and program-change parameters are not shown.
     - **A change is a parameter change** at the first sample of the next process call, in queues made before the audio thread starts. What the sound gives out (a meter, a setting it moved) is told to the controller on the host's turn.
     - **The state is both halves'**, in a `.vstpreset` of its own, as base64. **Its presets are `.vstpreset` files** for its class under `~/.vst3/presets/<vendor>/<plugin>` and the system's preset folders, where other hosts keep them; one saved from the block goes to the user's, never over another preset, and only a file in those folders is put in.
     - **A mono plugin on a stereo lane** runs twice or on the sides mixed, as for LV2; the second instance is a component alone, which hears the controller through the same relay as the first.
     - **The plugin's own window is its editor view** ([ADR-0025](adr/0025-plugin-windows.md)), put inside the host's X11 window. The frame it is given resizes that window, and is the run loop a Linux view asks for: its timers and descriptors are the host's PipeWire main loop's. `performEdit` goes to the audio thread through the host's queue and to the engine as ParamChanged, `beginEdit` and `endEdit` as ParamGesture; the engine's changes reach the controller through `setParamNormalized` thirty times a second. A plugin that says its buses changed is made again with its state; one whose latency changed is deactivated and activated again, with the audio thread kept away, and its latency read then.
   - **The node says what it is and asks for nothing.** It carries `application.name = Reverblabr`, a description such as `Reverblabr — Podcast` and our icon, and it sets `node.autoconnect = false` and `node.always-process = true`. It has **no `media.class` and no `media.role`**: it is neither a device nor an application stream, and a role is how a stream asks the policy for treatment. Every link to it is the link manager's ([ADR-0007](adr/0007-capture-and-linking.md)).
   - **A lane is a block's worth of ports**, one per channel position, laid out by the channel-mapping policy. A port finds what it carries by the block id it is named after, so a recompile that moves the blocks about needs no new ports.
   - **The real-time half is `rb::pw::SessionProcessor`**, which has no PipeWire in it at all. That is what lets one audio cycle be run, and checked, with no audio server anywhere near it: the allocation trap under GCC and RealtimeSanitizer under Clang both look at it directly (`pw.SessionProcessorTest.*`), and the node itself is measured against a real server in `tests/pw/test_sessionnode.cpp`.
4. **Telemetry** (`engine/rt`, `engine/core`, `app`). Meters, wire colours and state dots are read from a snapshot, never pushed through the facade: sixty signals a second to say what a pointer can say for nothing is not a design, it is a bill.
   - **The audio thread accumulates, it does not publish.** `rb::rt::ChannelMeter` holds the peak since anybody last looked, a sum of squares, a frame count and a clip latch, all lock-free; a cycle costs one compare-and-swap and three atomic adds whatever the quantum. "The latest value per cycle" would lose a single-sample click at quantum 32 and stutter at 2048, where a cycle happens 47 times a second.
   - **Measured inside the graph, not after it.** A buffer goes back to the pool as soon as nothing has to read it, so by the end of a cycle an intermediate block's buffer may hold what a later block wrote. `CompiledGraph::execute()` meters each block's outputs as that block finishes, which is the only place they are certainly its own.
   - **A meter belongs to its block**, not to a compiled graph, so an edit does not make every meter in the session blink.
   - `rb::core::TelemetrySampler` empties the accumulators sixty times a second on the engine thread and publishes one `TelemetrySnapshot` per session through an `rt::SeqlockValue`. The snapshot is a plain struct that owns nothing, and the seqlock lives in a shared-memory region (`core::PublishedSlot`), so a window in another process maps the very bytes a window in the engine's process points at ([ADR-0018](adr/0018-telemetry-in-shared-memory.md)).
   - `rb::ui::MeterHub` reads it on the frame tick (**one read per frame for the whole session, not one per meter**), turns amplitudes into decibels, and owns everything that is about time rather than about sound: how long a peak holds, how fast it falls, how long a clip light stays on, all in wall-clock time so that they look the same whatever the screen is doing.

5. **Capturing an application** (`engine/blocks`, `engine/core`). The Application source block (`rb::blocks::ApplicationSource`) is the first of the main blocks, and what it does and what the engine does are deliberately different things.
   - **The block is plain DSP.** By the time the audio reaches it, PipeWire has already summed every stream arriving at its ports (which is right, since they are different sounds from one application), so all that is left is to put whatever layout the application is playing in onto the session's stereo bus, through `dsp::ChannelMapper`.
   - **Its ports follow the application.** A stream playing to a 5.1 sink arrives as six channels, and every one needs a port of its own, because a link only ever joins two ports of the same channel and the folding is done with coefficients that were written down first ([ADR-0007]). `rb::core::capturePlan()` works out, from the session and the graph, what each source block should be capturing and in what layout (**the widest of the streams that are there**, and a stereo pair when none is), and the runtime tells the block through `PrepareSpec::inputLayout`.
   - **The match rule is what the session stores**: a binary name, a Flatpak id or the name an application calls itself, in that order, and never an id. A restarted application is the same application with new ids, so being captured again is not a special case: the link manager wants a *match*, and makes it true whenever the ports it needs appear. Measured at 21 ms across twenty restarts, against the 250 ms allowed.
   - **A layout that changes is an edit.** An application moved to another sink comes back with other channels; the runtime notices, publishes the ports the block now needs and lets the manager link them. Nothing about the session changed.
   - **The other side of a call is the microphone the application is itself recording from.** Nothing about it is stored and nobody chooses it: the engine finds the application's own capture stream, follows it back to whatever source is feeding it, and links that source to the block as well, so somebody changing the microphone in the application's own settings changes ours, with no edit anywhere. Measured at 75 ms, against the 500 ms allowed. The two groups arrive on **ports of their own** (`b1:in_FL` and `b1:in_mic_FL`), because a port carries one channel and both groups have a front left; `PrepareSpec::secondInputFrom` tells the block where the second begins.
   - **Split puts one side on each channel**: the microphone on the left, the application on the right, each folded to mono **inside our DSP**. Linking one stream into both of our ports would have PipeWire sum it and hand back 6 dB it never had. With the option on and nothing recording, the left side says nothing, which is true, rather than quietly becoming the application again.
   - **A URL is asked for, never opened.** A block may carry a URL to open when the session starts; the engine says so once per start (`OpenUrlRequested`) and the desktop opens it: KIO in the interface, `xdg-open` in the daemon that comes later. Starting a session that is already running is not a start and opens nothing.
   - **Which of an application's streams to take is a question about where they are going**, because a VoIP client plays the call to one device and its notifications to another. The block holds one of three modes (what it sends to the *default* output, to *any* output, or to the outputs *chosen* by name), and the manager answers it from the graph, through `EndpointMatch::playingTo`: where a stream is going is a matter of the links it has at this moment, not a property of the node, and a stream nothing has linked yet is judged by the target it asked for. An empty list of conditions is not the absence of one: "these outputs" with none chosen captures nothing.

6. **The device blocks** (`engine/blocks`, `engine/core`). The Output Device and the Input Device are the other main blocks, and the mirror image of the application source: the engine links, and the block decides what goes where.
   - **The block's ports are laid out to match the device**, so a link only ever joins two ports of the same channel. A stereo session on a 5.1 device lands on the front pair and says nothing on the centre or the surrounds, because a stereo session has nothing to say about them; a mono device gets half of each side, which is the policy and not a coincidence.
   - **The device is stored by `node.name`, or as "default"**, which follows `default.audio.sink`. Storing the resolved name instead would mean a session that followed the default until it was saved and then stopped. A change of default is followed within 250 ms, and nothing is left linked to the device that was.
   - **A device that is not there is not an error.** The block goes quiet, says so through its telemetry, and is linked again when a device of that name comes back: a headset that was unplugged is usually going to be plugged in again.
   - **The volume is an amplitude, smoothed over 20 ms**, applied inside our own DSP: half is half, which is −6.02 dB, and a slider dragged across its range does not step the signal.
   - **The Input Device is the same machine in reverse**: the device's capture ports are linked to the block's input ports, one per channel, and the block puts what arrives onto the stereo bus. A mono microphone is heard on both sides **at its own level**, because linking one port into two would have PipeWire sum it and hand back 6 dB it never had. A channel named by hand, such as input 3 to the left, takes that channel whole; a side that names a channel the device does not have hears silence, which is honest about a session set up for another machine.
   - **A session can never record itself.** An output block names a sink and an input block names a source, so the ring the feedback guard exists for cannot be asked for through them, and our own nodes are excluded from every match besides ([ADR-0007]).

7. **Capturing everything** (`engine/blocks`, `engine/core`). System Audio is the third main block, and the one that has to be careful about what it leaves out.
   - **Stream by stream, not from a monitor.** A sink's monitor carries what reaches that sink and nothing can be taken out of it; capturing each playback stream instead is what makes "everything except my chat client" something a person can ask for, and it is what lets alert sounds be left out ([ADR-0007]). PipeWire sums the streams at our ports, which is right: they are different sounds going to one place.
   - **A kind on its own is not a condition** unless the caller says so (`EndpointMatch::everyNodeOfKind`). "Any playback stream" is a thing somebody can mean, but it has to be asked for, or a rule that lost its name would capture the machine.
   - **What it leaves out**: alert sounds unless they are asked for, the applications in its exclusion list (by the same match rule the Application source stores and the inventory hands the picker), every node of ours from every session, and re-played streams, which would otherwise count the same audio twice.
   - **Two sessions capturing everything and playing to one device stay bounded**, because neither can see the other: our own nodes are in no match at all.

8. **Volume** (`engine/blocks`, `engine/dsp`). The gain block, and the first one with a limiter in it.
   - **Per cent means amplitude**: 100 % is the signal as it arrived, 200 % is twice it (6.02 dB), 400 % is four times it. A person matching one source against another thinks in "twice as loud", and the number in the file is the number the audio uses.
   - **Overdrive is the top of the slider, not a multiplier.** Turning it down brings the stored gain with it, so what is saved is what is heard.
   - **`dsp::LookaheadLimiter` is always in the signal path**, which is what makes the latency a constant the block reports. It delays the signal by its lookahead and applies the smallest gain the next lookahead of samples will need: a sliding-window minimum over a monotonic wedge, so the work is bounded and nothing is allocated. Below the ceiling it applies a gain of exactly one, and a null test against the delayed input proves it. The gain is linked across channels, so a peak on one side does not move the image.

9. **Dynamics** (`engine/blocks`, `engine/dsp`). A compressor above and an expander below, and the first block whose face is a curve.
   - **The curve is one pure function.** `dsp::outputDb(inputDb, settings)` says what a steady level comes out at, and the processor and the curve editor both read it. There is one definition of what the block does, so what is on the screen and what is in the sound cannot drift apart, which is the whole reason a curve editor is worth having.
   - **The interface reaches that function through `core::DynamicsCurve`**, which hands the block its parameters by id and answers with what comes out. The GUI may not use the DSP layer ([Layers](#layers)), and the alternative, a copy of the curve in QML, is exactly the drift the one definition is there to prevent; the wrapper keeps the one definition and costs a call.
   - **The shape and the timing are kept apart.** `DynamicsSettings` is the curve: thresholds, ratios, the knee, the expander's range, the makeup. `DynamicsTiming` is how long the sound takes to get there: attack, release, the expander's hold and which detector is following the signal. Only the first of the two is drawn.
   - **The gain reduction is smoothed, not the detector.** Smoothing the level going in would make the attack depend on how loud the signal is; smoothing the decibels coming out gives an attack that takes the same time whatever arrives, which is what the numbers on the controls promise. Measured within ±10 % at 44.1, 48 and 96 kHz.
   - **The peak detector is a sliding maximum over 5 ms**, two buckets swapped at the end of each window, which costs two comparisons a sample and never droops. A steady sine's samples run from nothing to its peak and back every cycle; feeding that straight to the curve would have the gain chasing the waveform and a steady tone would sit above the curve rather than on it. **It is fed the waveform's peak, not the samples'**: the sample itself, so an onset counts at once, and the three points between samples that the limiter's `TruePeakEstimator` interpolates, a quarter of a millisecond later. A tone at a quarter of the rate can put every sample at 0.707 of its peak, and read by its samples it would be compressed as if 3 dB quieter than it is. The RMS detector reads the samples, whose mean square is right whatever the phase.
   - **Stereo-linked**: the louder side decides and both sides get the same gain, so the image cannot wander.
   - **Nothing is smoothed but the makeup.** A threshold or a ratio that changes mid-drag changes where the signal is heading, and the attack and the release take it there at the speed they are set to. The makeup is added after all of that and has a 20 ms glide of its own.
   - **A ratio of infinity is the click past the end of the slider**, not a number on it: there is no room for ∞ on a control that runs to 20:1, and the number underneath is kept so that turning it off gives back the ratio that was there.
   - **Three numbers go to telemetry** (input level, output level and gain reduction, all in decibels), which is what the editor's live marker sits on.
   - **The Simple Compressor is this block with the settings chosen** (`blocks::SimpleCompressor`). Its one control is a mode (Off, Gentle, Moderate, Heavy, Voice or Broadcast), and each mode is a row of `DynamicsSettings` and `DynamicsTiming` handed to the same `DynamicsProcessor`, so a mode sounds exactly like the same numbers typed into a Dynamics block. **Off is a flat curve, not a bypass**: 1:1 and no makeup pass the signal bit for bit, and because the processor keeps running, switching to or from Off glides like any other change of mode instead of jumping the makeup out of the sound. The panel shows what a mode sets, read-only, through `core::CompressorModes`, for the same reason the curve editor goes through `core::DynamicsCurve`.
   - **The Multiband Compressor is three of these behind a crossover** (`blocks::MultibandCompressor`, `effect.multibandcompressor`). `dsp::ThreeBandCrossover` makes the bands with two fourth-order Linkwitz–Riley splits, each two Butterworth sections a side, as state-variable filters: the lower split makes the low band and the rest, the upper divides the rest. **The low band goes through the upper split's all-pass** (`FilterShape::AllPass`), because a Linkwitz–Riley pair adds up to an all-pass rather than to its input; with it all three bands add up to the two all-passes one after the other (every frequency at exactly 0 dB, only the phase moved), and without it two close splits dipped 6.7 dB between them. A moved split glides there in octaves over 30 ms, the filters worked out afresh each sample on the way; the two are held at least 1.5 times apart. Each band then has a `DynamicsProcessor` of its own (curve and timing, stereo-linked within the band, no expander), so a band's curve is the one the Dynamics block would draw for the same numbers, and the panel draws it with the same `ui::DynamicsPlot`. No latency: the splits are filters and nothing looks ahead. The three meter values are the bands' gain reductions; while the panel asks, `publishBands()` adds each band's level, output and reduction for the live marker on its curve.

10. **Meters** (`engine/blocks`). The Peak/RMS block is something to look at and nothing in the way: the audio comes out bit for bit as it went in, with no latency, so one can be dropped anywhere in a lane.
   - **The peak, the clip latch and the activity flag come from the graph**, which meters every block's output where it is made (see Telemetry above), so the block does not measure them twice.
   - What it adds is the calibrated part: a **root mean square over a rectangular 300 ms window**, kept as a running sum so the work is O(1) a sample. Plain RMS, so a sine whose peak is −18 dBFS reads −21.0 dB; the AES17 convention that adds 3.01 dB can come later as an option, and the panel says which one it is showing.
   - A block publishes numbers of its own through `PrepareSpec::meter`, such as a meter's levels or a dynamics block's gain reduction. **Null when nobody is watching**, which a block has to cope with.

11. **Wave** (`engine/blocks`). A test signal: a sine, square, triangle or sawtooth at any frequency from 20 Hz to 20 kHz, or white or pink noise, at a level from −80 to 0 dBFS, on the left, the right or both. Listed under Outputs, because what it is for is testing what is plugged into one, and it has an output connector rather than a device of its own, so the tone can go through a meter, a Volume or anything else on its way to a device.
   - **It is a source because of its ports, not its list.** No inputs and an output is what makes the compiler take it as the start of a lane and the runtime give it no capture port. Deciding by category would have made a block listed under Outputs unrunnable.
   - **Band-limited edges.** The square and the sawtooth have their jumps smoothed by a polyBLEP and the triangle its corners by a polyBLAMP, so a 15 kHz square does not fold back into the audible band as a whistle of its own.
   - **Nothing jumps.** The level, the frequency and the side each glide over 20 ms, so dragging the slider or moving the tone from one side to the other does not click through the speaker under test.
   - **Held at full scale.** Pink noise has the odd sample past its nominal peak, and a generator that clipped the device it was testing would be testing itself.
   - Noise comes from a xorshift generator and the pink filter is Paul Kellet's, so nothing on the real-time thread allocates or locks.

12. **Recorder** (`engine/blocks`, `engine/record`, `engine/core`). Writes what arrives at it to a file and passes it on, sample for sample and with no latency, so a lane can go on to a device after it and several Recorders can hang off the same audio.
   - **The block is the audio thread's half and nothing more.** Each cycle it copies what it hears into its tap (`rt::AudioTap`) and goes back to the audio. A tap holds ten seconds, at the session's rate or at 96 kHz, whichever is more; a cycle that does not fit is dropped whole and counted, never waited for, and what goes on to the next block is untouched.
   - **The tap belongs to the runtime, not to the block** (`PrepareSpec::recording`, given to a block that says `BlockInfo::recordsAudio`). A block replaced by a fresh one for a new layout is handed the same tap, so the recording carries on across it. The rate travels in the tap as a marker pinned to the frame it starts at, and only when it changes.
   - **`record::RecordingWriter` puts the taps on the disk**, on a thread of its own per running session, which may wait for the disk as long as it likes. It is plain C++ and libsndfile (`engine/record`), so all of it runs in a test with no audio server. Commands are queued and carried out in order: the runtime tells it to record a Recorder before the graph that runs it goes live, and to finish one after the graph that stopped running it has; stopping a session waits for every file to be closed and reported. A recording starts with the next audio that arrives, never with what sat in the tap before, and a file is made only when there is audio for it. **A change of rate starts a new file**: a file has one rate.
   - **Formats**: WAV (RF64 only if it passes 4 GB), AIFF, FLAC, MP3, Ogg Opus and Ogg Vorbis, through libsndfile. 16 and 24 bits are dithered, triangular and one step either side, and rounded by us rather than truncated. A file is made with `O_EXCL`, so nothing anybody already has is overwritten.
   - **A file at a rate of its own** (44.1, 48, 88.2 or 96 kHz rather than the session's) is converted by soxr on the writer's thread, never on the audio thread, and keeps its rate when PipeWire moves the session to another: only the conversion into it changes. An Opus file in a session at a rate Opus does not take is made at 48 kHz.
   - **Room on the disk** is looked at before a file starts and twice a second while it is written. Under a gigabyte, the recording says so once and carries on (`recording.lowDiskSpace`); under 64 MB the file is finished while it still can be (closed properly, everything before it kept), and the recording stops with `recording.failed` and `DiskFull`. A disk that runs out in the middle of a write leaves a header nobody could write; stopping short of it leaves a whole file.
   - **Commands apply at a frame, not at a moment.** `start()`, `finish()`, and the pause, resume and split a person asks for through `ControlRecording` each note how far the tap has got when they are asked for, and the writer applies them at exactly that frame however late it gets to them; no drain goes past a command still waiting. So a pause and a resume leave the two parts joined with nothing missing and nothing twice, and a split ends one file on the frame before the next begins, named with the next counter.
   - **File limits** are the writer's too, and counted in the session's frames, so they fall on exact samples: a new file every so many minutes, hours or megabytes; the recording ending by itself after so many minutes or hours (`RecordingStopped`, "timeLimit"); and silence (every channel under a threshold from −96 to −20 dB for so many seconds) removed, split on (the file ends with the silence and the next begins with the sound), or stopped at ("silence"). The writer, which sees every sample anyway, is what measures the silence; the audio thread does no more than it did. An AIFF, whose header cannot say it is longer than 4 GB, splits itself at 2 GB or 24 hours. A Recorder's settings changed while it records reach the recording at once: a limit now, a format or a name from the next file.
   - **M4A**, AAC-LC with FFmpeg's own encoder or Apple Lossless, goes through the distribution's FFmpeg rather than libsndfile, and only where that FFmpeg has the encoder: the engine opens each one at start-up (`record::probeEncoders`), and a format whose encoder does not open is left out of the catalogue's choices, listed with "encoderMissing" so a panel can say to install the full FFmpeg or to use Opus or FLAC. No patented encoder is ever chosen or bundled. An M4A is written in fragments a second long, each with its own index, so a crash leaves a file that plays to its last fragment with nothing to repair; when it is finished it is copied into a regular MP4 in its place, with the encoder's priming marked to be skipped, for the players that are fussy about fragments.
   - **Tags** go on each file when it is finished, through TagLib on the writer's thread: ID3v2.4 for MP3, Vorbis comments for FLAC, Opus and Vorbis, a RIFF INFO list and an ID3v2 chunk for WAV, ID3v2 for AIFF, MP4 atoms for M4A. Every field is text in UTF-8 and may hold the file-name tokens (and `%year`), filled in for each file, so a Track of `%counter` numbers the files a recording splits into. A file whose tags could not be written is whole and says so (`recording.tagsNotWritten`); a file is checked to be what it is said to be first, because TagLib would find an MP3 frame in a FLAC and write an ID3v2 tag onto it.
   - **An application's pauses** are left out when its source asks for that (the Application source's "fill gaps with silence", off). The runtime tells each Recorder's tap which of the node's input lanes its pauses are read from (the lanes of the sources upstream of it, if every one of them is an application that leaves its pauses out, and none otherwise, since a microphone beside it is a sound that goes on), and a cycle in which none of those lanes had audio arriving is not recorded, so the two parts join. Otherwise the pause is written as the silence it is.
   - **Names** come from a pattern (`%session %date %time` by default, with `%counter` and `%block` besides), made safe for every file system and never landing on a file that is there: " (2)" goes after the name, or the counter counts up. The default folder is Reverblabr in the music folder. The settings are read when a file starts, so a change takes effect at the next one.
   - **A crash leaves a file that plays, and the next start makes it whole.** A WAV's or an AIFF's length is written into its header every two seconds and the data synced. Every recording in progress has an entry in a journal (`$XDG_STATE_HOME/reverblabr/recordings`), made before its first frame and removed once it is closed; the engine starts by repairing what the journal names from a process that has gone, measuring what reached the disk and writing it into the header: RF64 for a file that passed 4 GB, STREAMINFO's total for a FLAC.
   - **What it says**: `RecordingFileStarted` and `RecordingFileFinished` through the facade, every file started being finished, and `recording.failed`, `recording.overflow` or `recording.lowDiskSpace` on the block's tile when a file could not be made or written, when the disk did not keep up, or when it is getting full.
   - **The recordings index** (`core::RecordingLibrary`) is the engine's, not the window's: a file is finished by the engine, and later by a daemon with no window open, so a list the interface kept would miss what was recorded while it was closed. It is SQLite at `$XDG_DATA_HOME/reverblabr/library.db`, through QtSql (a Qt module with no GUI in it, which the engine layer allows). A file gets a row, marked in progress, as it starts; as it finishes it is read back through on a worker thread (`record::summarise`: the length that decodes, the rate, the channels and 512 peaks for its waveform), and a file libsndfile cannot read keeps what the Recorder counted. `RescanRecordings`, and every start of the engine, drops the rows whose file has gone, finishes one a crash left in progress, and reads again a file that has changed size. `RecordingsChanged` carries one session's list, and the Files tab is that list: its actions (the folder in the file manager, Open With…, the freedesktop trash) are KIO's, in the interface, and after a trash the index is asked to look.
   - **Listening to a recording** (`core::RecordingPlayer`) is a player's stream of its own, `reverblabr.preview` with the Music role (`pw::PreviewStream`), which the session manager links to the default output like any player's. It is never linked to a session's node, the engine's link manager never touches it, and it asks the graph for nothing: PipeWire converts the file's rate and channels. A thread of its own reads the file (`record::AudioFileReader`) two seconds ahead into an `rt::AudioTap`, and the stream's audio thread only copies out of it. A seek starts the stream again from the new place. `PreviewRecording`, `PausePreview`, `SeekPreview` and `StopPreview` are answered by `PreviewChanged`; `pw.preview` checks that a session beside it, on its own device or the same one, keeps its rate, its quantum, its cycles and its sound.
   - **The Recording Inspector** is a window per file (`RecordingInspectorWindow`, opened from the Files tab and kept one a file by the main window). The engine answers for it: `GetRecording` gives the index row with 512 peaks and the tags read from the file now; `RenameRecording` renames the file in its folder, keeping its extension and never writing over another, and the index with it (`RecordingRenamed`, `recording.renameRefused`); `SetRecordingTags` writes the tags with TagLib and answers with what the file then holds (`recording.tagsNotSaved`). The outline is `WaveformItem`, two scene-graph nodes of bars (as many as the width has room for, each the loudest of the peaks under it), with the played part in the live colour. `record::AudioFileReader` reads M4A through FFmpeg, seeking a few packets early so a lossy decoder's first frame is whole, and lands on the frame; the index reads a finished file's outline and tags through it, so every format the Recorder writes has both.

13. **Filters** (`engine/dsp/biquad.h`, `engine/blocks`). Every filter block is built from second-order sections, and there is one of those, not one per block.
   - **Designed once, run two ways.** `dsp::designBiquad()` gives a section's coefficients from its shape (low-pass, high-pass, peaking, low and high shelf), frequency, Q and gain, through the bilinear transform with the frequency warped to land where it was asked for; `dsp::biquadResponse()` gives its exact response, for a test to measure a block against and a curve to draw. The same transfer function runs as a direct form (`dsp::Biquad`) where the coefficients hold still, or as a state-variable filter integrated by the trapezoidal rule (`dsp::Svf`, coefficients from `dsp::designSvf()`) where they move. **The state-variable form keeps its state as the charge on two integrators**, so its coefficients can change every sample (a cutoff dragged across its range) without it thumping or running away, which a direct form swapped to a different filter mid-signal can do. Both are held to the design within 0.01 dB for every shape.
   - **Low Pass Filter** (`effect.lowpass`). Butterworth, so the pass band is flat and the cutoff is 3 dB down at either slope: 12 dB an octave is one section, 24 dB is two with the fourth-order Qs (not one section twice, which would be 6 dB down at the cutoff and dull below it). The cutoff glides in octaves over 30 ms and the coefficients are worked out every sample while it moves and not at all once it arrives. Both slopes run all the time and the output fades between them over 20 ms, so a change of slope does not click. It starts at 20 kHz, where it changes nothing anybody can hear.
   - **High Pass Filter** (`effect.highpass`). The same block keeping the other side: `blocks::CutoffFilter` is made from a kind (type id, shape, range and start), and the Low Pass and the High Pass are that with a low-pass from 200 Hz to 20 kHz starting at 20 kHz, and a high-pass from 20 Hz to 2 kHz starting at 20 Hz. The interface's face and panel are shared too, and read the range and the start from the engine's description rather than holding a copy.
   - **Bass & Treble** (`effect.basstreble`). A low shelf at 100 Hz and a high shelf at 10 kHz, each ±12 dB, at a Q of 0.7071: the steepest slope that does not overshoot, so a lift never booms past its own gain. At 0 dB a state-variable shelf passes its input straight through, so the block at its defaults changes not one bit. Each gain glides in decibels over 20 ms, and a shelf is designed again every sample only while its gain moves.
   - **10-Band EQ** (`effect.equalizer10`). Ten peaking bells at the octave centres, 31.5 Hz to 16 kHz, ±12 dB at a Q of 1.41 (an octave between the half-gain points), plus a preamp. *Keep level* lowers the output by the highest point of the curve, looked at each band's centre and half-way between two, and worked out again only when a band moves. Flat, it changes not one bit. Twenty factory presets ship with it; the panel's Flatten puts every band and the preamp back as one edit (`SessionModel::setParams`, which the Mixer's fades brought in), so one Ctrl+Z brings the whole shape back.
   - **Parametric EQ** (`advanced.parametriceq`). Up to ten bands placed by hand (a bell, a shelf, a pass filter, a notch or a band-pass, 20 Hz to 20 kHz, Q 0.1 to 18, ±18 dB), in ten fixed slots of six parameters (`bandNUsed`, `bandNOn`, `bandNType`, `bandNFrequency`, `bandNGain`, `bandNQ`), so adding and deleting a band moves no other. Frequency and Q glide in octaves and gain in decibels; a band that starts, stops or changes type fades out, changes at the sample the fade ends, and fades back in. The curve editor draws the block's own cascade through `core::EqualizerCurve` and `ui::EqualizerPlot`, the same way the Dynamics curve is drawn, and one grab over the plot moves the band nearest the press.
   - **The live spectrum behind the curve**. Any block's output can be looked at this way. `EngineFacade::analyse()` names one block per session; its `rt::BlockMeter` then copies the block's first two outputs into an `rt::AudioTap` where the graph meters them (a flag read otherwise, and the ring is kept for as long as the meter), and the telemetry sampler drains it on the engine thread into `dsp::SpectrumAnalyser`: 4096-sample Hann frames at half overlap, transformed four times as long with our `RealFft`, folded into 96 bands evenly spaced in octaves by the power each takes, averaged over 250 ms. The snapshot carries the block's id and its bands; the panel asks while it is shown and lets go when it closes, so nothing is copied or worked out while no curve is open.
   - **Before and after, of one ear, and a value a band**. The analysed block's first two **inputs** are copied too, into a second ring, before the block runs and after the paths meeting it have been lined up, so the spectrum before it is of the same moment as the one after; a block with no inputs has none. `analyse()` takes a channel (both mixed, or the first or the second alone) for a block that works on one ear. A block may publish up to `rt::kMaxBandValues` (128: two for each of the 64-band block's bands) numbers for its panel with `rt::BlockMeter::publishBands()`, through a seqlock so a reader gets one cycle's bands whole; they are stored only while the block is analysed, and the snapshot shows only those published since the look began. `core::BlockAnalysis` is the sampler's own work on the analysed block, apart so a test can run it over a graph played offline. The snapshot grew for this, so the shared-memory layout went to version 2, and to 3 with the 128 values (ADR-0018).
   - **Dehum** (`advanced.dehum`). A notch at the mains frequency (50 or 60 Hz, tunable 2 Hz either way) and at each harmonic up to the tenth, 2 Hz wide at the base and wider by the square root of the harmonic's number, so a note half way between two harmonics is left within a fifth of a decibel. Amount is the depth, 6 dB a step to 60: each notch's output mixed with its input, so at 0 the signal passes bit for bit. Every notch runs all the time, and the base and the depth glide. **Auto** (off by default) puts the notches on a hum that drifts: `dsp::HumTracker`, a phase-locked loop on the fundamental (the input turned down to 0 Hz by an oscillator at the loop's frequency, a three-pole 20 Hz low-pass, a proportional-and-integral loop updated about 3000 times a second), cross-checked against the 2nd and 3rd harmonics turned down the same way. It looks between 48 and 62 Hz, starting from Base; it is 3 Hz wide until locked, then narrower the noisier the phase. It counts as locked once the fundamental's phase has kept still for a quarter of a second, and otherwise holds where it was, so silence or program with nothing steady at the base never moves the notches. The notches are redesigned from its estimate every 16 samples, 3 Hz wide at the base rather than 2 so a hum moving under them stays inside; the estimate glides, and switching Auto off glides the notches back to Base. The block publishes where the base is and whether it has locked, for the tile and the panel.
   - **One ear's audiogram, and the rule that fits it** (`dsp::Audiogram`, `dsp::fitAudiogram()`, `core::fitFromAudiogram()`). A listening block keeps one ear's audiogram among its parameters (eleven points from 125 Hz to 8 kHz, each measured or not, heard or not, with an optional "too loud" level, in dB HL or dBFS). A pure function turns it and the block's band centres into, per band, a gain for soft, average and loud sound and a ceiling, by a public rule (half gain, or NAL-R), with soft ≥ average ≥ loud and nothing above the ceiling; a band that asks for more than the most gain, or that the ear did not hear, is marked. **Fit from audiogram** writes the result as `band<N>…` settings in one list edit, so one undo takes it back. Details, sources and the reviewed tables: [fitting-rules.md](fitting-rules.md).

14. **Link manager** (`engine/pw`). The engine says **which links should exist**; `rb::pw::LinkManager` makes that true and keeps it true. It is a reconciler, not a set of event handlers: every registry change asks the same question, so a restart, a move to another sink and a change of channel layout all need no special case.
   - **Links follow ports, not nodes.** A stream's ports appear after its node and are made again when it moves to a sink with another layout, so a link is made when the ports it needs are there.
   - **Endpoints are matched, not addressed**: a `node.name`, an application's binary, name or Flatpak id, and a channel position, never a runtime id. A match that names no condition matches nothing, so a mistake is silent about the graph rather than loud in it. Our own nodes, alert sounds and re-played streams are left out unless the caller says otherwise.
   - **A channel that is not there is not guessed at.** Putting the signal on a channel the user did not choose is worse than not linking.
   - **It only ever touches its own links**, and never duplicates one somebody else has already made, because a port sums every link into it. A link of ours is removed by letting go of the proxy that made it; every one carries `object.linger = false`, so they all vanish if the process is killed and the captured application carries on playing.
   - A burst of changes (a default-device change moves many things at once) is allowed to settle before a pass, and a link the server refuses is tried again after a wait that doubles.
   - **A stream the policy moves is let go of first**. To move a stream to a sink with another channel layout, the policy lets go of its own link, gives the stream the new layout, remaking its ports, and links it again. A link of ours still on the old ports goes with them, and the stream could be left **suspended** where it landed: silent there, and unable to take another layout, so an application captured in the Application block's default mode and moved to a mono device and back played on the left of the stereo output only. So:
     - **our links go at once** when the "default" metadata asks for a stream to be moved (`target.object`, which the mirror reports as `moveRequested`), when the default output changes under a stream that follows it, or when the policy lets go of its own link from it. These are destroyed on the spot, not on the next turn of the event loop as other links are: a turn is long enough for the policy to begin;
     - **the stream is linked again once it has landed**: a link of the policy's from it is up (`PwLink::state` Paused or Active) into a node whose channels are the stream's, or a second has gone by for a stream that keeps a layout of its own. A link of ours made while the policy's is still agreeing its format can make the policy's fail;
     - **a stream left suspended is woken.** The policy owns the metadata and hears of a move before we do, so it sometimes starts first. A stream we were listening to that lands `Suspended` (`PwNode::state`) for more than 100 ms gets a passive link of ours on its new port, which starts it again, and which goes as soon as it runs.
15. **Each audio cycle**, on the real-time thread, the node:
   - turns denormals off for the cycle, and starts its own clock
   - applies queued parameter changes, so a value set between two cycles is heard from the first sample of this one. A change names a block by slot, and one for a block the live graph does not have is dropped rather than kept: the block it was meant for is gone.
   - maps the port buffers; a port with no buffer is one nothing is linked to, which is the only time PipeWire gives none. An input with no buffer is silence, an output with none is skipped, and **every output buffer that exists is written in every cycle**, with silence where the graph has nothing to say.
   - **An output still holding last cycle's buffer gets none**. After each cycle the server passes an output's buffer on to its links and marks the port as needing data again. While a port's buffers are being made again, as after a quantum change, there can be a cycle in which the filter writes and nothing passes the buffer on; a buffer asked for in the next cycle would then be queued behind it, and that channel would play a cycle late, a cycle apart from its neighbours, for as long as the link lasted. So a port whose io still says it has data is given no buffer that cycle: the one it holds goes out, a cycle late once, and the next cycle is in step. The session node counts these (`SessionTelemetry::unreadOutputs`), and a plugin host does the same for its own outputs.
   - runs the compiled graph for this cycle's frame count, whatever it is: buffers are made for 8192 frames, so a change of quantum costs nothing
   - writes its outputs and updates the telemetry slots
   - **A cycle at a rate the graph was not prepared for comes out silent**, and the node asks the engine for a graph prepared at the new rate. Re-preparing allocates, so the real-time thread never does it ([ADR-0008](adr/0008-filter-runtime.md)).
   - **What it reports:** cycles, xruns, the DSP load as a fraction of the cycle's own period (peak since the figure was last read, and the last cycle's), the quantum and rate it saw, and a bit per lane saying whether audio was arriving, which every block is handed with its cycle (`ProcessContext::sourcePresent`) and the Recorder reads to tell silence from a source that has gone away.
   - **What counts as an xrun.** Spike S2 found PipeWire's own `SPA_IO_CLOCK_FLAG_XRUN_RECOVER` never set and the graph position jumping instead, so a cycle that does not start where the last one ended is the sign that matters. But the position also moves when the node is handed to another driver or the graph is restarted under it, and neither of those has lost anybody a cycle, so those are recognised (by `clock.id` and `clock.cycle`) and left out. A driver that says its timestamps jumped says so separately, and the driver's own accumulated `clock.xrun` estimate settles the cases the position cannot see.
16. **Edits while running.** A changed session is recompiled off the real-time thread and handed to it between two cycles, by a blocking `pw_loop_invoke()` on the node's data loop that only swaps pointers ([ADR-0008](adr/0008-filter-runtime.md)). When the call returns, the retired graph is out of use and the engine thread frees it; nothing is freed on the real-time thread. `rb::pw::SessionNode::update()` does the whole edit in one call, because the order is what makes it safe and inaudible:
   - **Down first.** The lanes the edit can be heard through are ramped to silence over the fade (10 ms by default). The engine thread waits for the audio thread to say the ramp is done: about one fade, which the engine thread may spend and the GUI thread never does. If the node isn't being scheduled the ramp can't finish, and it gives up waiting: silence cannot click.
   - **Then the ports it needs**, before the graph that uses them. A port that is wanted again keeps its handle, and with it every link that ends on it, so editing the middle of a lane never disturbs what is plugged into its ends.
   - **Then the graph**, handed over while the changed lanes are silent.
   - **Then the ports it no longer needs**, now that the graph that used them has gone.
   - **Back up**, and from there the edit is audible.
   - **Which lanes are those?** `rb::graph::changedBlocks()` (`engine/graph/graphdiff.h`) compares the old and new specs: a block is named when it is new, gone, a different instance, or enabled or disabled, when what arrives at it comes from somewhere else, or when anything upstream of it was named. A block whose *output* has been wired elsewhere is not named: what leaves a block depends on what arrives at it and on its own state, never on who is listening. It errs towards naming one: fading a lane that hadn't changed costs a few milliseconds of dip, missing one costs a click.
   - **A lane that is not named is not touched at all.** Its samples are copied through, not multiplied by a gain of one, so a session being edited in one place goes on bit-for-bit everywhere else.
   - **Switching a block off is not an edit like the others.** It gets a crossfade of its own, inside the graph: `NodeSpec::crossfadeSamples` makes the block go on running for the length of the fade, and the graph mixes what the block makes of the signal with the signal itself, equal-power, from one to the other. So the sound never dips; it *becomes* the other version of itself. A caller that asks for that must **not** also name the block in `SessionUpdate::changedBlocks`, or the lane would dip around a fade that needed no dip.
   - **A bypassed block still holds the signal back by as long as it would have delayed it.** Otherwise switching a block off would shift it against every path running beside it, and a merge point that was lined up would no longer be. A block that is silenced rather than passed through needs no delay line: delaying silence gives silence. The fade also waits for that delay to fill before it starts, because a fresh delay line and a block's first samples are both silence, and fading into silence is a dip where there should be none.
   - **A delay added on purpose is not latency.** The Sync block holds a lane back as its whole job, so its `latencySamples` is zero and what it adds is `Block::intendedDelaySamples()` instead: compensation lining the other paths up with it would undo it, and switching the block off is exactly how somebody takes it away, so a bypass must not keep it either. It is reported with a path's delay for a person to read, and never compensated. It changes from cycle to cycle without a recompile; a change of setting is faded across between two read heads of one delay line (`DelayLine::processChannelTwoTaps`) rather than jumped. The Time Shift is the same kind of delay, set by its transport rather than a number: its head can be minutes behind live, and `intendedDelaySamples()` says how many samples. **Its history is too big for the audio thread to write to disk**, so beyond ten minutes the block keeps a file through a thread of its own (`TimeShiftSpill`): the audio thread hands each cycle over through an `rt::AudioTap`, and reads audio older than its last minute in memory from a ring the thread fills ahead of the head. The file is unlinked as soon as it is opened. The thread does all there is to do and then sleeps for 20 ms, a hundredth of either ring's headroom, or until the block goes; the audio thread never wakes it. A history memory holds on its own has no file and no thread.
   - **A change of quantum needs none of this**: buffers are made for 8192 frames. A change of rate needs all of it, plus re-preparing every block, which happens off the real-time thread between the node asking (`rateChangeNeeded`) and the new graph arriving.

## Working with PipeWire and WirePlumber

See [ADR-0002](adr/0002-native-pipewire-and-wireplumber-as-peer.md).

- **libpipewire directly.** We use the registry, filter nodes, the link factory and the `default` metadata. No libwireplumber, and no GLib main loop.
- **One connection, kept.** `rb::pw::Connection` (`engine/pw/connection.h`) runs PipeWire's main loop on the engine thread's Qt event loop, through a `QSocketNotifier` on the loop's file descriptor, so registry events and replies arrive where the engine's state lives with no lock ([ADR-0008](adr/0008-filter-runtime.md)). PipeWire or WirePlumber restarting moves it to a wait and it tries again after a delay that doubles up to a limit. Nothing of PipeWire's is destroyed from inside a loop iteration: the loop is still delivering messages there, and would come back to freed memory.
- **An always-current mirror.** `rb::pw::RegistryMirror` keeps a typed copy of the nodes, ports, links, clients and devices the engine cares about, so an answer about the graph is never a round trip. A registry announcement says an object exists; what it *is* comes from binding it, which is a round trip further on, so the mirror asks the server for a sync and says `ready()` once everything announced has also been described. Proxies of objects that have gone are let go on the next turn of the event loop rather than inside the callback that reported them.
- **The graph's clock and driver are mirrored too**. The mirror follows the server's `settings` metadata (`clock.rate`, `clock.quantum`, the forced values), so a quantum forced from outside is known within a second, and each node's `node.driver-id`, which the server rewrites as nodes move between drivers. `graphDriver()` names the driver of the graph a running session of ours is in, or else the default sink's (the default sink itself when, idle, it drives nothing but could).
- **A proxy the server never made is let go, not destroyed.** A global can go away between the mirror asking to bind it and the server reading the request: a client that connects, looks at the graph and leaves does exactly that, and does it many times a second. Telling the server to destroy something it never made is a protocol error, and the server closes the connection over it, which would take every running session node with it. So a proxy with no bound id is simply dropped, and the core frees it when the connection ends.
- **The inventory is a reading of the mirror, not another copy of it.** `rb::pw::Inventory` (`engine/pw/inventory.h`) is what the pickers and the blocks ask about: applications grouped from their streams, inputs, outputs and the defaults. It is worked out from nodes, ports and links alone, which is what lets it be checked against a graph written out by hand. Streams are classified as an application's own, a re-play or an alert ([ADR-0007](adr/0007-capture-and-linking.md)), and an application is identified by a **match rule** (`binary:`, `flatpak:`, `name:` or `node:`), which is what a session file stores, since a stream's `node.name` is not unique. `rb::pw::InventoryWatcher` keeps it current: a burst of registry changes is gathered up into one inventory, no later than 200 ms after the first of them, and an inventory that says nothing new is not sent at all.
- **Ids are for now, serials are for later.** PipeWire reuses object ids, so anything that must mean the same object over time, such as a saved reference or a link the manager is waiting for, holds `object.serial`. A reconnect empties the mirror and fills it again, and every id from before it is meaningless.
- **Our own nodes are marked.** A node that carries `reverblabr.virtual-device` is one of the virtual devices below, and is **never** ours: it is a device, meant to be seen and picked. Otherwise a node is ours when it belongs to **our own connection's client**, when its `application.name` is ours, or when its `node.name` carries our prefix, so a caller can leave them out without knowing how we name things. The client is the one the server gave our connection's id to (`rb::pw::Connection::clientId()`), not "a client with our process id": a process can hold more than one connection, and taking the last one seen would make which nodes count as ours depend on the order they arrived in.
- **WirePlumber keeps the policy.** It picks default devices, routes ordinary streams, restores volumes and manages Bluetooth profiles. We read its decisions from the `default` metadata and never override them. We ship no WirePlumber scripts or configuration that the app needs in order to work. The only configuration we ever write is PipeWire's own drop-in for the virtual devices a user asks for, described below ([ADR-0013](adr/0013-virtual-devices.md)).
- **Fan-out only.** Capturing an application adds links from its stream to us. The stream keeps playing to its device, and we never move or unlink another application's stream.
- **Tidy nodes.** Our nodes don't auto-connect (`node.autoconnect = false`). They carry `application.name = Reverblabr` and a description such as `Reverblabr — Podcast`, so they read well in qpwgraph, the Plasma audio applet and other tools.
- **Channel mapping is explicit.** A PipeWire input port sums every link into it at unity gain, so a link is never used to mix channels: a centre channel linked into both L and R would come out 3 dB hot, and a stereo pair linked into a mono port 6 dB hot. Only ports with the same channel position are linked, and all mixing happens in `rb::dsp::ChannelMapper` (`engine/dsp/channelmap.h`) with these coefficients:

  | Into the session's stereo bus | Left | Right |
  |---|---|---|
  | `MONO` | 1.0 | 1.0 |
  | `FL` / `FR` | 1.0 | 1.0 |
  | `FC` | 0.707 (−3 dB) | 0.707 |
  | `LFE` | dropped | dropped |
  | `RL` / `SL` | 0.707 | — |
  | `RR` / `SR` | — | 0.707 |
  | `AUXn` | as the block assigns it | |

  | Out of the stereo bus | From left | From right |
  |---|---|---|
  | `FL` / `FR` | 1.0 | 1.0 |
  | `MONO` | 0.5 (−6 dB) | 0.5 |
  | `FC`, `LFE`, surrounds | silent | silent |
  | `AUXn` | as the block assigns it | |

  A mono source reaches both sides at the level it went in at, because the two sides carry the same signal rather than two halves of one. Two correlated full-scale channels summed to mono come out at full scale. A stereo signal has nothing to say through a centre, a subwoofer or a surround, so those stay silent unless the block's advanced settings say otherwise.
- **Feedback guard.** Sound fed back into its own source runs away: each trip round the ring adds the loop's gain, and within a second or two it is as loud as the hardware allows. PipeWire will happily make such a link; nothing in it looks for the ring. So before a link is made, and again whenever the graph changes around one, `rb::pw::findFeedbackPath()` asks whether the sound could already get back round, and a link that would close a ring is refused or let go. It is reported as `routing.feedbackLoop`, with the way round as its argument, and the rest of the session carries on.
  - The walk is over **nodes**, because a node passes what arrives at it on to what leaves it. That is what makes capturing the monitor of a sink we are playing to a ring of one: a sink and its monitor are the same node.
  - It follows **`node.link-group`** as well as links. A loopback, a filter chain, a combined sink and an echo canceller are each two nodes joined inside PipeWire, and a ring through one of them is invisible in the links alone.
  - An existing link is asked the same question with itself left out of the walk, which is how it learns that it is the one closing a ring that has appeared around it.
  - **Somebody else's link is a change too**. A patchbay joining a device's monitor back into what a session records closes a ring with no port or node changing, so every link another client makes asks again, within one settle time. Links appear in bursts and all the time, so they never put off a pass already waiting, and our own coming back through the registry are ignored.
  - Only the link that closes the ring goes, or rather every link of ours between the same two nodes, since the walk is over nodes and a lane's two channels are two links: letting go of one leaves the ring standing on the other. Those links stop counting for the guard at once, for the rest of the pass and until the server has announced their removal; otherwise the next of our links looked at would seem to close the same ring, and both halves of the session would go, each reported as a ring of its own.
- **Capturing the whole system** merges the individual application streams rather than listening to a device monitor. That makes it possible to exclude single applications, and our own nodes and re-played streams are always excluded.
- **Virtual devices are listed twice**. A virtual output (a null sink applications are sent to) is also an input, recorded from its monitor ports; a virtual microphone (`Audio/Source/Virtual`) is also an output, played into through the ports that feed it. That is how a session processes every application's sound, and how it hands a processed microphone to a call. A card's monitor is not offered. A null sink does not set `node.virtual`, so a device counts as virtual by that, by its media class, by `factory.name = support.null-audio-sink`, or by the marker the devices Reverblabr makes carry. Device blocks still name a device by `node.name`; the plan decides from the graph whether the name is a source or a sink, and when two nodes share a name for a moment the newer one, by serial, is meant.

- **Virtual devices are the one thing we leave behind** ([ADR-0013](adr/0013-virtual-devices.md)). `rb::pw::VirtualDeviceManager` (`engine/pw/virtualdevicemanager.h`) keeps the user's virtual outputs and microphones in a PipeWire drop-in per scope, which is the truth about them, disabled ones included, and which PipeWire makes them from at every start. Each change is written first and then made live: a node through the `adapter` factory with `object.linger = true`, so it outlives the app, or a node destroyed through the registry. Links and session nodes keep `object.linger = false`; only these devices linger.
  - **A rename creates before it destroys.** A node's description cannot be changed from outside, so a rename makes a new node under the same `node.name` and lets the old one go only once the new one has its ports; destroying first sends the apps playing into it to the default device for a moment, which is heard.
  - **Reconciling**, when the graph has been read and after every change, makes each enabled device the graph lacks, never a second node of a name already in use, and destroys each marked node that no enabled entry in a readable file accounts for. A scope whose file cannot be read is left alone. A device something else removed is not made again by a graph change, only by the next reconcile.
  - **All users' devices are read-only to the engine.** Their file under `/etc` is written by a privileged helper; the engine lists them, makes their live nodes in this user's session, and reconciles again when told the file changed.
- **The all-users helper** (`helper/`). `reverblabr-virtualdevices-helper` is a KAuth helper the system bus starts as root, for the one polkit action `io.github.reverblabr.virtualdevices.write` (`auth_admin_keep`; refused to inactive sessions). The desktop's polkit agent shows the administrator's password prompt.
  - **It receives two lists, never file text**: `devices`, the whole list the system file is to hold, and `previous`, the list the caller changed. The file must still hold `previous`, or nothing is written (`ChangedElsewhere`): on a machine with several users, another user's change would otherwise vanish. Any other argument, an entry of any other shape, more than 64 devices or an overlong name is refused before anything is read, and the names then pass the engine's own check.
  - **It writes exactly one path**, `/etc/pipewire/pipewire.conf.d/90-reverblabr-virtual-devices-system.conf`, making its directory when missing (Fedora has no `/etc/pipewire`), removing it for an empty list, and never replacing a file Reverblabr did not write. What it does is `reverblabr-helper-action`, a library of its own with a layer rule that forbids KDE Frameworks, Qt GUI and PipeWire, so it is tested as it runs, against a directory of the test's own.
  - **The interface asks it, not the engine**, which may not use KDE Frameworks. `core::planSystemDeviceChange()` works out the two lists from the engine's last listing, `rb::ui::SystemDeviceWriter` runs the action one request at a time, and the `VirtualDevices` model sends a change there whenever the device is an all-users one. Once the file is written the model asks the engine to reload, which makes the live node; a cancelled or refused prompt changes nothing and is reported like any other refusal.
  - **It is optional.** `RB_BUILD_AUTH_HELPER` (on when KF6Auth is found) builds it and lets the app call it; without it every all-users change is refused as having no helper. No test ever reaches the system bus: the tests give the writer a stand-in.

How capture and linking behave was measured by the capture spike; [ADR-0007](adr/0007-capture-and-linking.md) records the rules that follow. In short:
- Nodes and ports are identified by `object.serial`, because PipeWire reuses ids.
- Links follow port appearance. A stream's ports appear after its node, and are re-created, with reused ids, when the stream moves to a sink with another layout.
- A captured stream already carries its user volume and mute, and it has the layout of the sink it plays to (six ports on a 5.1 sink, one on a mono sink). Source blocks take whatever layout arrives and convert it in DSP.
- Re-played streams (loopbacks, filter chains, combined sinks, echo cancellers) carry `node.link-group`, and alert sounds carry `media.role = Notification` or an `event.id`.
- The session node has no `media.class`. PulseAudio clients, including Plasma's microphone indicator, don't see it; a Bluetooth microphone needs a separate `Stream/Input/Audio` capture node.

## Threads

| Thread | Runs | Rules |
|---|---|---|
| **PipeWire data thread** (real-time, scheduled by PipeWire) | the session nodes' process callbacks | the real-time rules below |
| **Engine thread** (`QThread`) | session model, compiler, facade implementation, the 60 Hz telemetry sampler, and PipeWire's main loop (registry events, link and port changes) | owns all engine state; no other thread touches it directly |
| **GUI thread** | QML and the facade client | calls into the engine are asynchronous; nothing may block it for more than 1 ms |
| **Recording writer** (`std::thread`, one per running session with a Recorder) | draining the Recorders' taps into files, encoding, header updates | fed from lock-free rings; may wait for the disk as long as it likes, and never makes the real-time thread wait |
| **Workers** (later) | analysis | fed from lock-free rings; never block the real-time thread |

Data crosses threads only through these channels:

| From → to | Channel | Type in `engine/rt` |
|---|---|---|
| GUI ↔ engine | the facade: queued calls and signals | — |
| engine → real-time | a fixed-capacity single-producer, single-consumer parameter queue, and the graph handover | `SpscQueue` |
| real-time → recording writer | each Recorder's tap: ten seconds of frames, and its rate pinned to the frame it starts at | `AudioTap` |
| real-time → engine | telemetry slots, an event queue, and a retire queue for anything the real-time thread gives up (graphs don't need it) | `SeqlockValue` and `TripleBuffer`, `SpscQueue`, `RetireQueue` |
| real-time → the log | fixed-size records a normal thread formats and writes | `RealtimeLogger` |
| engine → real-time, inside a block | data a block builds on the engine thread when a setting changes, handed over whole through one atomic pointer, and given back through the block's own retire queue: the FIR Filter's impulse response, read from its file, resampled and transformed | `std::atomic<T *>`, `RetireQueue` |

Which of the two "latest state" carriers a telemetry slot uses is a question of size: `SeqlockValue` copies the value on every read and every write, and suits a handful of floats; `TripleBuffer` hands over a slot and suits a whole frame of meter data. Both let the writer carry on without ever waiting, and both let the reader miss values, which is what a meter wants.

PipeWire's main loop has no thread of its own. The engine thread drives it with a `QSocketNotifier` on the loop's file descriptor, so PipeWire events arrive where the engine's state lives, and no lock is needed ([ADR-0008](adr/0008-filter-runtime.md)).

## Real-time rules

Everything reachable from a process callback follows these rules:

- **No allocation and no freeing.** Memory is prepared in `prepare()`. Objects the audio thread stops using go to `rt::RetireQueue` and are freed elsewhere; if the queue is full it refuses, and the caller keeps the object rather than freeing it there.
- **No locks, waits or condition variables.** Use atomics, lock-free queues and seqlocks.
- **No system calls:** no file or network I/O and no direct logging. `rt::RealtimeLogger` writes fixed-size records into a ring that a normal thread drains, formats and timestamps, so nothing on the audio thread needs a timestamp.
  - One exception is `rt::monotonicNanos()` (`engine/rt/clock.h`), which is how a process callback times itself for the DSP load figure. `CLOCK_MONOTONIC` is answered by the vDSO: it reads a page the kernel keeps up to date, with no system call, no lock and no allocation. It is the only clock the audio thread reads: twice a cycle, and twice a block while the data loop is running long (below).
  - The other is `rt::readThreadRun()` (`engine/rt/runwatch.h`): one `getrusage(RUSAGE_THREAD)` per session node per cycle, at its end, and `sched_getscheduler()` at the moment a session decides to give way. Both are real system calls. Neither takes a lock the audio thread could wait on, allocates or blocks. They are there because the alternative is the kernel ending the process.
- **No exceptions.** Every processing function is `noexcept`.
- **Bounded work.** Nothing loops over a structure that can grow while running.
- **Denormals are flushed to zero** (FTZ/DAZ) on the real-time thread.
- **Any cycle length from 1 to 8192 frames** is handled, and a NULL input buffer means silence.
- **Parameter changes** arrive through the parameter queue at the start of a cycle and are smoothed inside the block, so they never step.

These rules are checked by tools, not only in review:

- Processing functions carry the `RB_NONBLOCKING` annotation (`engine/rt/realtime.h`). With Clang, the compiler rejects allocations, locks and calls to unannotated functions inside them (`-Wfunction-effects`).
- The `rtsan` preset builds with Clang's RealtimeSanitizer, which stops a test at the first allocation, lock or system call inside an annotated function.
- With GCC, an allocation trap in the DSP test kit catches allocations on real-time paths.

### When a session is too heavy

rtkit makes the data loop real-time and gives the process `RLIMIT_RTTIME`: 200 ms of CPU without a sleep, with the soft limit equal to the hard one. The kernel counts from the moment a real-time thread last woke, and at the limit sends SIGKILL with no warning. A loop sleeps between cycles; one whose every cycle overruns never does, and a session with too many heavy blocks for the machine, or a quantum set too small, would take the whole program with it.

- **Watched:** each session node reads, at the end of its cycle, how long its thread has run since it last slept (`rt::RunWatch`, from the thread's CPU time and its voluntary context switches). The nodes share one loop, so the CPU time counts all of them.
- **Given way:** once the loop has gone on from one cycle into the next without resting for 50 ms, a session taking at least a quarter of its cycle stops running its blocks and puts out silence; at 100 ms every session on the loop does. The cycles are then short and the loop sleeps again. One long cycle that ends in a sleep is not an overrun, however long it is.
- **Named:** from 25 ms of run, a cycle times its blocks (`CompiledGraph::execute` with a span), so the session can publish the three that cost the most.
- **Said:** the runtime sees the node's overload count move and the engine reports `session.overloaded` on the heaviest block's tile.
- **Back:** the next graph (any edit) or another quantum runs the blocks again; if that did not help, the session gives way again within 50 ms.
- **Not real-time:** rtkit can refuse. Once a user has asked too often too quickly it says no (its burst limit), and a thread it refused is held to no limit, so it has nothing to give way to and goes on. The node says which it is: `SessionTelemetry::realtime` from its first cycle, and `longRunsNotRealtime` counts the runs it went on through for that reason, once each. `RB_PW_NO_REALTIME` runs the connection without asking at all.

## Session data model

Sessions are plain JSON files in `$XDG_DATA_HOME/reverblabr/sessions/<uuid>.rbsession`:

```json
{
  "schemaVersion": 1,
  "id": "0d9c8b6e-5f3a-4c1e-9b7d-2a6f4e8c1b35",
  "name": "Podcast",
  "notes": "",
  "settings": { "autoConnect": true, "sampleRate": "auto", "latency": "default", "autoRun": "off" },
  "blocks": [
    { "id": "b1", "type": "source.application", "nickname": null, "enabled": true,
      "pos": [40, 120], "params": { "match": { "binary": "firefox" } }, "preset": null },
    { "id": "b2", "type": "meter.peakrms", "nickname": null, "enabled": true,
      "pos": [220, 120], "params": {}, "preset": null },
    { "id": "b3", "type": "output.device", "nickname": null, "enabled": true,
      "pos": [400, 120], "params": { "device": "default" }, "preset": null }
  ],
  "wires": [
    { "from": ["b1", 0], "to": ["b2", 0] },
    { "from": ["b2", 0], "to": ["b3", 0] }
  ],
  "timers": [
    { "id": "5b0e3c1a-8f2d-4d6e-b7a9-1c4e2f6a8d30", "enabled": true, "repeat": "weekdays",
      "time": "07:30", "duration": 5400, "quitApplications": false }
  ],
  "automations": []
}
```

- **`schemaVersion`** selects the migration path when the format changes.
- **Atomic save:** the file is written to a temporary file, flushed with `fsync`, then renamed over the old one.
- **Locale-independent data:** numbers use `.` as the decimal separator, and dates are ISO 8601. Values are formatted for the user's locale only on screen.
- **Stable references:** devices are stored by `node.name` and applications by match rules (binary, name, Flatpak ID), never by runtime object IDs.
- **Robust loading:** a block type this version doesn't know is kept and flagged, not dropped. A corrupt file is backed up (`.corrupt-<timestamp>`) and reported with an error code, and the app still starts.
- **Timers** (`core/timers.h`) start the session at set times, through the background engine's systemd user timers ([below](#timers)). Each has an `id` (a letter or a digit, then letters, digits, `-` and `_`: it becomes part of a unit's file name and of a command line; an id another session has is refused), `enabled`, `repeat` (`once` with a `date`, `yyyy-MM-dd`; `daily`; `weekdays`; or `days` with `days`, `["mon", "thu"]`), `time` (`HH:mm`, local time), `duration` in seconds (at most a week) and `quitApplications`. A timer this version can't read, such as one with a repeat from a later version, is kept in the file as it is and never run. An imported session's timers get new ids, as the session does.
- **Reserved field:** `automations` is there so that a later feature doesn't break older files.
- **Block type IDs** are `<category>.<name>` and never change:

## Engine facade

The facade is also Reverblabr's public API, `io.github.reverblabr.Engine1` on the session bus: [docs/dbus-api.md](dbus-api.md) documents it, and [ADR-0020](adr/0020-public-dbus-api.md) is its compatibility promise.

- **Methods:**
  - sessions: `ListSessions`, `CreateSession`, `OpenSession`, `SaveSession`, `CloseSession`, `DeleteSession`
  - editing: `ApplyEdit`, `SetParam`, `Undo` / `Redo`, `GetUndoState`
  - running: `Start`, `Stop`, `GetSessionState`, and `ControlRecording` (pause, resume or split a Recorder)
  - inventory: applications, inputs, outputs and the defaults
  - the audio system: `GetAudioSystem`, and `ReconnectAudioSystem` for the Retry a person presses
  - virtual devices ([ADR-0013](adr/0013-virtual-devices.md)): `ListVirtualDevices`, `CreateVirtualDevice`, `RenameVirtualDevice`, `SetVirtualDeviceEnabled`, `DeleteVirtualDevice`, and `ReloadVirtualDevices` for after the all-users helper has written its file
- **Signals:**
  - a full session snapshot followed by numbered patches; the GUI resynchronises when it sees a gap
  - `StateChanged` (idle, starting, running, error)
  - `InventoryChanged`
  - `VirtualDevicesChanged`, and `VirtualDeviceCreated` with the new device's id before the list that shows it. **Every call about virtual devices is answered exactly once**, by the list or by a refusal (`device.virtualNotCreated`, `device.virtualRefused`, whose reason is the manager's own word for why), so an interface can mark a row as waiting and know when to stop; the manager's own announcements wait while a call is being answered.
  - `AudioSystemChanged`: where the connection stands, the names and versions of the server and its session manager, the driving node's description, and the graph's rate and quantum whether or not a session of ours is running. **The engine is the client, so the engine is what knows**; a GUI that hard-codes the name is a GUI that lies the first time the engine speaks to something else.
  - `RecordingFileStarted` and `RecordingFileFinished` with `{frames, sampleRate, seconds}`, for every file a Recorder writes; `RecordingPaused` in answer to `ControlRecording`; `RecordingStopped` when a Recorder ends its recording by itself
  - `Error(code, argsJson)`
- **Telemetry** (meters, activity) never travels through signals. The facade hands out a snapshot reader instead.
- **A mock engine** implements the same interface with fake devices and animated meters, so GUI work doesn't wait for the real engine.

## Telemetry path

```
real-time thread               engine thread, 60 Hz            GUI thread, each frame
per-block slots          ──►   read and reset the        ──►   MeterHub reads the snapshot,
 · peak since last read        accumulators, publish           converts to dB, and applies
 · RMS sum and count           one seqlock snapshot            peak hold and decay in
 · clip latch, activity        per session                     wall-clock time
 · block values (for example gain reduction)
```

The real-time side accumulates instead of storing "the latest value". A latest-value scheme loses short peaks when cycles are small, and stutters when they are long (a 1024-frame cycle at 48 kHz is only about 47 updates a second). The snapshot lives in shared memory ([ADR-0018](adr/0018-telemetry-in-shared-memory.md)): a window on the daemon maps it read-only and reads it on its own frame tick, exactly as a window in the engine's process reads it through a pointer.

**How long a peak holds is a parameter of the block, and what tells the hub is the block model.** `peakHold` belongs to the Peak/RMS block and travels in the session file; the waiting is done in `MeterHub`, in wall-clock time. Carrying the one to the other is `rb::ui::BlockModel`'s, because it is what already follows every block in the session; a face only draws and a panel only writes the choice back to the session. A hub told by something on the screen knows about the blocks somebody has looked at and no others, which is why a meter's hold once reached the hub only after its panel had been opened.

On the GUI side one ticker drives the whole canvas: a single frame-synced animation advances one property, and every meter, wire and marker reads it ([ADR-0009](adr/0009-canvas-rendering.md)). Meters are scene-graph items that rewrite their geometry, not QML item trees. The measured cost of a canvas with 50 blocks, 60 wires and 50 meters is 1.3 ms per frame on the GUI thread, of which the wires' moving dash is 0.7 ms.

## The window

The GUI is a Qt Quick application built on Kirigami, drawn by our own control style in the Reverblabr appearances and by the native Breeze controls in *Follow system* ([ADR-0012](adr/0012-reverblabr-look.md)), and it talks to the engine through nothing but the facade: the same calls a D-Bus client would make ([ADR-0003](adr/0003-in-process-engine-behind-facade.md)).

- **KWin draws the title bar in *Follow system*.** The design has the session tabs, Run/Stop and the elapsed timer inside a title bar of its own. On Plasma that would mean giving up the user's decoration theme, their window rules, their tiling and their snapping in order to redraw three things they already have, so the content moves into a **toolbar row directly under the title bar** and the window is a window like any other. **Superseded for the Reverblabr appearances by [ADR-0012](adr/0012-reverblabr-look.md)**: there the window is frameless and its top row is the design's own header, and moving, resizing, snapping and tiling stay with the compositor through `startSystemMove()` and `startSystemResize()`, which is what answers the objection above. What is still given up is the decoration theme and the user's button layout, and *Follow system* keeps this bullet as it stands.
- **Our own title bar, in the Reverblabr appearances** ([ADR-0012](adr/0012-reverblabr-look.md)). The window is `Qt.FramelessWindowHint`, fixed at start with the control style, and `ToolBarRow` is its title bar: after Run come the theme button, the menu button and minimise, maximise and close (`WindowButton`, the prototype's 28-pixel squares). **The empty part of the row is the window's handle**: a `MouseArea` behind everything in the row, so a tab or a button keeps its own presses, hands a drag to the compositor with `startSystemMove()`, maximises on a double click and asks for the window menu on a right click; the tab list is only as wide as its tabs so the room past them is the handle's. `ResizeGrips` is a 6-pixel band inside each edge and a 16-pixel square in each corner that hand a press to `startSystemResize()`, so the compositor still snaps and tiles. The window is transparent outside its 8-pixel corners (it asks for an alpha surface at start, and the header's and status bar's own backgrounds take the corners), with a hairline round it and **the design's shadow drawn by the compositor**: `WindowFrame` cuts `0 24px 64px rgba(0,0,0,.45)` into KWindowShadow's eight tiles once the window's surface exists, the corner tiles reaching in by the radius so the transparent corners show shadow. Maximised, the window is square, with no hairline, no shadow and no grips. **The window menu is the compositor's**, asked for through Qt's Wayland client internals (optional at build time; without them, and off Wayland, a smaller menu of ours). **The menus are behind the menu button** until Ctrl+M shows the menu bar, which then sits under the title bar (the two slots of the `ApplicationWindow` are filled the other way round from *Follow system*), and the choice is kept per kind of window in `WindowState`. The button's menus are a second set of the bar's actions, since a menu belongs to one parent, and `tst_titlebar.qml` holds them together entry for entry.
- **Colours are roles, not values, in *Follow system*.** `AppColors` maps each of the design's tokens onto a `Kirigami.Theme` role, so with Breeze the window looks like the design and with any other scheme, and whatever accent colour somebody has chosen, it looks like their desktop. Only what a scheme has no role for is a constant: the "signal flowing" orange, which says something about this application rather than about the desktop, and the category tints the block icons carry. Breeze's own separator formula is used for our own lines, so a line of ours sits at the same weight as one drawn by a widget beside it. **Superseded for the Reverblabr appearances by [ADR-0012](adr/0012-reverblabr-look.md)**: there every token holds the design's own value (its two palettes, its fonts and its pixel sizes), and the same names map onto these roles only in *Follow system*, so the QML reads one set of names in both.
- **Depth is two roles, derived rather than chosen**. A scheme names one background; the interface needs three depths: the surface, a panel header or hovered row *above* it, and a meter's trough or a plot's well cut *into* it. `AppColors.surface2` and `AppColors.well` are both a fraction of the way from the surface toward the text colour, which is lighter on a dark scheme and darker on a light one, and is the only direction certain to exist. Reaching for `canvas` instead, which is what everything did before, gives a step of 1.02 on Breeze's dark scheme, and means "the canvas" somewhere else in the same window.
- **Three token files, two sources** ([ADR-0012](adr/0012-reverblabr-look.md)). `AppColors`, `AppFonts` and `AppMetrics` are the only places the QML names a colour, a font or a corner; `tools.design-tokens` fails on a hex colour, a font size, a scheme role or a radius written anywhere else. Each name has two values: the design prototype's own (two fixed palettes, Noto Sans and JetBrains Mono at its pixel scale, its corners and gaps) and the desktop's (the scheme roles, fonts and Kirigami units the window used before). `rb::ui::Appearance` says which is in force: *Reverblabr dark* (the default), *Reverblabr light* or *Follow system*, from **Settings → Appearance**. The choice is kept as a word in `reverblabrrc` and applied while the window is open. The two faces are bundled under OFL-1.1 (`app/fonts/`) and registered at start. In the Reverblabr appearances they are also the application's own font. Two values deliberately differ from the prototype: the ink on the live orange stays dark, and on a light canvas the category tints stay at their 3:1 lightness.
- **Our own control style, chosen at start** ([ADR-0012](adr/0012-reverblabr-look.md)). `app/style` is a Qt Quick Controls style named `Reverblabr`, built on Basic: the buttons, tool buttons, check boxes, radio buttons, switches, tabs, list rows, tool bars, the menu bar and the split handle are drawn from the tokens, and anything it does not draw yet falls back to Basic. `Appearance::useStyleFor()` picks it before the QML engine loads when the stored appearance is a Reverblabr one, and the desktop's style otherwise; Qt cannot restyle an open window, so a change of appearance reaches the controls at the next start, while colours and fonts follow at once. Under it, **what is not QML gets the design's colours too**: `AppColors` hands its tokens to `Appearance::setDesignColors()`, which sets the application palette (what Basic's controls draw with) and leaves the tokens on the application object for a **Kirigami platform plugin** (`app/kirigami`, installed as `kf6/kirigami/platform/Reverblabr.so`), which Kirigami loads by the style's name and which makes every `Kirigami.Theme` colour set from them; without it, Kirigami falls back to its built-in light theme. Text is drawn by the font engine, hinted, as the browser draws the prototype. The QML suite runs twice: under Basic in *Follow system*, standing in for the desktop's style, and under this style in *Reverblabr dark* on a Breeze Light desktop (`qml.mainwindow.reverblabr-style`), the case in which anything still drawn with the platform's palette would show.
- **The style's value controls**. Sliders, lists that drop down, text fields and areas, numbers and scroll bars are the prototype's too: a field is the field colour in a one-pixel border that takes the accent while it is typed into or its list is open, 26 pixels high; a list ends in the prototype's chevron and opens in the same frame below its field; a scroll bar is the browser's thin one, a four-pixel thumb in the well colour, shown whenever there is more to scroll to. **Every slider is the one the prototype draws for itself**, a Volume tile's (a four-pixel trough filled to the value and a ring), rather than the browser's range input its panels leave to whichever browser shows them: a panel's at sixteen pixels in the accent, a face's at twelve in its block's tint. The groove and the ring are two files of the interface (`SliderGroove`, `SliderHandle`) that the style's `Slider` and a tile's `FaceSlider` both draw with, so a face looks the same under either style. The application a block captures is chosen from a combo box whose list is the application picker, with the program's icon given as Kirigami's style hint, which the desktop style and ours both draw.
- **Everything that pops up is the style's too** ([ADR-0012](adr/0012-reverblabr-look.md)). The prototype draws no menu, tooltip or dialog, only one popover, the settings panel; so the style's `Menu`, `MenuItem`, `MenuSeparator`, `ToolTip`, `Popup`, `Dialog` and `DialogButtonBox` are drawn in its language: the surface in a border, six-pixel corners, the resting shadow (only for a popup drawn inside the window; one in a window of its own has the compositor's), rows at a control's height, a menu row's key muted at its far end (`Appearance::shortcutText()`), the prototype's tick and chevron. `Pane` is drawn as its zoom control's frame. **None of them reads the palette**: the platform hands a menu or a tooltip a palette of its own from the desktop, which in a plain window is what they get. The style's `ApplicationWindow` sets the design's body text on the window, so a label, which names no font, takes it from there rather than the platform's default for labels. The Kirigami plugin puts its view set, which is what a Kirigami dialog is drawn in, on the surface, and sets Kirigami's corner to the popover's, handed over with the colours as `cornerRadius`. Where the prototype draws a glyph of its own (the header's "+", Run and Stop, a menu's tick and arrow, and the theme and window buttons of the title bar), `AppGlyphs` names it (`app/icons/glyph.*.svg`); *Follow system* keeps the icon theme's. With all of that the style's, *Reverblabr dark* became the default.
- **One object for what the window knows about the engine.** `rb::ui::AppShell` holds which session is in front, what it is doing, how long it has been running and what the status bar says; the toolbar row, the status bar and the menus all read it rather than working it out three times and disagreeing. **The engine is handed to it, never made by it**: the application gives it the real one and a test gives it the mock, and the QML between them cannot tell which it has.
- **Telemetry still does not come through the facade.** Where to read a session's snapshot is handed to the shell separately, as a function of the session id: a pointer into the engine in this process, or a mapping of the daemon's memory ([ADR-0018](adr/0018-telemetry-in-shared-memory.md)). A mapping comes and goes with its session and its daemon, so `AppShell::telemetryMoved()` tells `Meters` to read afresh.
- **A dash, not a zero.** A session that is not running has no load and no rate, and a `0 %` would be a measurement of something. The status bar shows the dash until the node itself says it is running, and the xrun count is shown whether or not there are any: a count that appears only when something has gone wrong is a count nobody knows to look for.
- **The session tabs read as tabs**: the one in front is underlined in the accent and set heavier, the others are muted, and nothing is filled: a tab filled with the accent read as the selected row of a list. The strip ends with a `+`, which is the Session menu's own New Session action. Each tab keeps its close button, which the design lacks, and its live dot, shown only while that session runs.
- **Every saved session in a table of its own**: **Session → All Sessions…** opens the Sessions window, one of it, above the main window, framed as the Virtual Devices window is. `rb::ui::SessionOverview` is its model, drawn from `SessionsListed` rather than from the tabs: the engine already reads every session file to list them, so each entry says its sources, how many recordings it has made and, while it runs, when it started (`core::sessionListEntry`, shared by the engine and the mock); nothing is opened just to be shown. The level is the loudest peak of any block, read from each running session's telemetry twenty times a second while the window is visible, falling at a meter's pace. Run on a session only on disk opens it (into a tab of the main window, where it can be seen and changed) and starts it once it has opened. The columns (which are shown, their order, widths and the sort) are the person's, kept in the state file under `[Tables]`, like a window's size; the name cannot be hidden. **Auto Run** is a column: a check box per session, `setAutoRun()`, set as the session's own `setSessionSetting` edit, and on a session only on disk after it has opened, as Run opens it; the row says the new value from the patch. Timers are not a column: they are the Schedule tab's, one session at a time.
- **The transport reads status, clock, action**: what the session is doing, for how long, and what to do about it, in the order a person asks. Run/Stop is the one filled button in the row (the accent colour to start, the live colour to stop) and ends the row, so it is where the eye ends up and it does not move when the status word changes width. The clock is set larger than the text beside it, bright only while it counts, and keeps the width of `00:00:00` from the start so it does not shove the row about as the hours arrive. Writing on the live colour is near-black on both schemes: white on either orange is about 2:1.
- **The clock is a clock on a wall.** The elapsed time counts wall-clock seconds and keeps counting through an xrun, because that is what somebody watching it means by it. Past a day the days are counted separately, as `2d 3:04:05`, since `51:04:05` is a number nobody reads as two days.
- **What the status bar says about the audio system comes from the engine.** The rate and the cycle are read from the node's own telemetry while a session of ours runs, and from the graph's clock as `AudioSystemChanged` gives it while none does, so there is a dash only when neither has said; and the server's name and the state of the connection from `AudioSystemChanged`. The name is always shown, working or not: a reading that appears only when something has gone wrong is a reading nobody knows to look for.
- **Nothing touches the window's edge**. One margin, `Kirigami.Units.largeSpacing`, keeps everything a person reads or presses off the window's sides and off the sides of the pane it is in: the toolbar row and the status bar at both ends, the sidebar's tabs, search field and library, the Info tab's forms, and the canvas's corner controls. A theme unit rather than a number, so it grows with the font and the scale. A test walks the toolbar, the status bar and the sidebar and fails on anything within it of either side.
- **An action, not a copy of one.** Every menu item and the button beside it are the same `Action`, so they cannot disagree about whether something is enabled or what it is called. Run/Stop is greyed out rather than hidden when there is no session, and Report Bug is greyed out while this build has nowhere to send one: quietly sending somebody to the wrong tracker is worse than a menu item they cannot press.
- **Undo is the engine's history, named by the interface**. `SessionModel` repeats what `undoStateChanged` says for the session in front, and the Edit menu's entries name the step they would take ("Undo Move Block") from a table of the interface's words keyed by the engine's `edit.*` codes, as the error messages are. Switching tabs switches whose history they follow. A drag still in the live queue is sent before an undo, or it would arrive afterwards and put back what the undo took away. A text field with the focus keeps Ctrl+Z for its own typing.
- **The Info tab holds the session's settings, not the application's.** Its title, automatic connections, sample rate, latency and Auto Run travel with the session file, so each is an edit through the facade and comes back as a patch, which is what makes the menu's Automatic Connections, the tab's switch and the toggle on the canvas three ways to one setting rather than three settings. **The canvas says which mode it is in**, in words at its top left and outside the zoom transform, because a mode that changes what dropping a block does belongs where the block is dropped; the status bar's hint follows it. The "Audio system" box beside them is read-only: what the graph runs at is the session manager's business ([ADR-0002](adr/0002-native-pipewire-and-wireplumber-as-peer.md)) and not ours to set from a sidebar.
- **The Schedule tab is the session's timers** (`SchedulePane.qml`, `TimerDialog.qml`), read from `SessionModel.timers` and changed with `setTimer` and `removeTimer` edits, so each change is one step to undo and the background engine follows the patch to its systemd timers ([Timers](#timers)). The dialog's Save waits until `SessionModel.timerIsValid()` says the session would take the timer, and shows the calendar expression systemd will be given. Quitting the captured applications asks first, in a prompt of its own, before the box is ticked. A window running its own engine says that timers need the background one, as the Info tab does for Auto Run.
- **Window size and the splitter go in the state file**, not the settings file: KConfig keeps the two apart on purpose, and a window size is something the application noticed rather than something somebody chose. It is written when the window closes, because a drag of a window edge is a hundred resizes.

## A block's tile

A tile is glanced at, so it is two parts that look like two: a header saying which block it is, a rule, and the block's **face** under it with the whole width of the tile. Faces come from a register (`BlockFaces`), and a block with no face of its own gets the generic one drawn from what its descriptors say.

- **A face says one thing.** An icon face is an icon and one line: the device for a device block, the program for an Application block, what is being taken for System Audio. The rest of what it knows (that a device is the default one, how many streams an application has going) is in a tooltip on the face and in the settings panel, where there is room for it. Whether a block is live is said once, by the state dot in the header.
- **A Volume tile is a value and a slider**: the percentage in the fixed-width face with "gain" beside it, over a thin track filled in the effects colour up to a ring, grey when the block is off. It has no meter; whether sound is going through is the header's dot and the wires.
- **A tile is carried by its header**. A drag that starts anywhere else does not move it; a press there still selects it, and a double click there still opens its settings. The header shows an open hand, the face the ordinary arrow.
- **A face's controls work where they are**. The tile's own pointer area is *behind* everything on it rather than over it, so a slider on a face, or the clip light on a meter, takes its own presses and the tile gets only what is left. It used to be over everything, and the Volume and Wave sliders were drawn but could not be moved.

## The settings panel

Every block's settings are shown by one panel, which opens beside that block on the canvas.

- **A block's settings belong to that block**, so they open next to it rather than in a pane at the side of the window: to its right, flipping to its left when there is no room and then clamped inside the viewport, with a caret pointing back at it. The canvas places it, being the only thing that knows where a tile has got to.
- **It is outside the zoom transform.** Scaled with the tiles its text would blur at 200 % and be unreadable at 50 %, and its controls would be the wrong size to hit, so the canvas works out where the block has got to *in viewport pixels* and puts the panel there at its own size.
- **A double click opens it**, as do Enter and the block menu's Settings. A single click only selects: opening on every click put a panel up whenever somebody only meant to pick a block, and took over the one they had open. A tile still reports a click separately from a press, so that a gesture which became a drag is never mistaken for one.
- **It can be pulled off its block**, and **a panel pulled off lives on its own**. Detaching is for keeping a block's settings in view while working on the rest of the canvas, so a detached panel does not close when another block is opened or the canvas is clicked, does not go back beside its block when its block is asked for again (it comes to the top where it is), and only its own attach control docks it. Any number can be out at once, one per block; the docked panel beside the block in hand is a separate, single thing, and a press on nothing or Escape closes only that one. A detached panel says so three ways: the caret goes, the border takes the accent colour and the shadow deepens. Its header is the handle it is dragged by, and every panel is kept inside the viewport, so resizing the window cannot leave one half outside.
- **Where the detached panels were left is remembered**, per session, in the state file beside the window's size (`WindowState.detachedPanels`), and they come back when the session does: on a tab switch and at start. The state file and not the session file: where a panel sat on this screen is something the application noticed, not something the session does, and moving one is not an edit to undo. F2 belongs to the window alone and renames the selected block; with several panels open, a panel's own F2 could not say which it meant.
- **A press on the card stays on the card**. The card is a rectangle, which takes no press of its own, so a press that no control took, on a docked panel's header or between two rows, used to fall through to the canvas, where a press on nothing closes the settings. The card now has a pointer area of its own behind everything in it. **The name is renamed where it is**: a double-click on it in the header turns it into a field, docked or detached, and F2 does the same; there is no pencil beside it.
- **It is as tall as what is in it**, up to what the viewport allows, and scrolls inside that. The body's height is asked of the block's own panel rather than of the scroll view around it, whose `implicitHeight` is zero; a panel sized from its layout and a layout sized from its panel settle on an answer a few pixels short rather than failing.

- **Every panel ends the same way**: a bin at the left that takes the block off the canvas (one undoable step, like Del, so it asks nothing), and "Presets:" with the list and its menu at the right. A block whose settings say they have no use for presets (a meter) has no footer at all.
- **A panel is a form, as the designs draw it**: muted labels against their boxes, lined up in one column ("Audio device", "Left channel", "Right channel"), a value read in the accent at the end of its line over a slider at full width, and what most people never need folded under a heading with a chevron (`CollapsibleSection`), starting folded. The body has the window's margin at its sides, and **the card, not its content, says how wide it is**: a footer that asked for a fixed width once made the card's column lay everything out wider than the card, and a test now opens every block's settings and fails on anything past the margin. A choice that needs a reason is in bold with the reason under it, indented to its text; the Application block's three ways of choosing what is captured are radio buttons in sight rather than a list box, because which one is chosen is the thing most worth seeing about that block.
- **The parameter descriptors are the panel.** A block declares its parameters once (id, type, range, choices, unit, taper), and the generic panel is generated from that, so a new block needs no new interface code. The same description already drives the DSP, the presets and the session file; the engine hands it to the interface as the block catalogue (`GetBlockCatalogue`), and `rb::ui::BlockCatalogue` is where the interface keeps it. **It holds no words**: everything in it is a stable id, and the names a person reads are the interface's, translated and keyed by them.
- **A block with a panel of its own is the exception**, for one whose settings are a *shape* (a transfer curve, a set of mixer strips, a transport) rather than a list of settings. `BlockPanels` maps a type id to a component; a block with no entry gets the generic panel, which is not a lesser one and is also the accessible fallback for the blocks that do have one.
- **One docked panel, whichever block is showing.** It is opened by naming a block rather than created for one, so moving from one tile to the next is a change of one string. The detached ones are rows in a list the canvas keeps, each a panel of the same kind.
- **A read-only parameter is a readout**, not a control. It is something the block says about itself, such as a gain reduction or a stream count, and offering to change it would be a lie.
- **A number on the screen is for a person; a number in a file is for a machine.** Values are written in the reader's locale, with a decimal comma in de_DE, and travel to the engine as JSON numbers, which have no locale at all.
- **`rb::ui::SessionModel` follows the engine's copy rather than keeping one.** A snapshot when the session opens, and every edit after that as a numbered patch applied with the engine's own `applyEdit`, so the two cannot drift; a gap in the numbering asks for the snapshot again rather than papering over it. A turned knob is the one deliberate exception (the engine sends no patch for `SetParam`, because sixty a second to tell a client what it just did would be sixty messages a second saying nothing), so the value is kept as it is sent, and an undo, which *is* a patch, overwrites it.
- **A drag costs sixty edits a second, not one per mouse event.** Values are coalesced at 60 Hz, the first goes at once so the control never feels behind the pointer, and the last always goes when the button comes up. A whole drag is one undo step, because `EditHistory` merges a gesture.

## Meters on the screen

One component draws every meter in the window: a block's tile, its panel, the tray, the mixer.

- **Scene-graph nodes, not `Canvas`.** A meter changes sixty times a second and there may be fifty of them; a level change costs one geometry update and no new items, no bindings and no text layout. `Canvas` would rasterise each of them on the GUI thread every frame ([ADR-0009](adr/0009-canvas-rendering.md)). Measured at **0.010 ms a frame for fifty meters** in the optimised build, against the 1 ms allowed.
- **One mapping from decibels to a place on the meter**, read by the bars in C++ and by the scale in QML. A bar drawn with one curve beside a scale drawn with another is a meter that lies about itself, and it is the kind of lie nobody notices until they are trying to match two sources by eye. It is piecewise linear in decibels through three anchors: the top 12 dB take 45 % of the meter, because the difference between −3 and −1 dBFS matters and the difference between −50 and −48 does not.
- **The hold and the decay are the hub's, once for the whole session**, and they are in wall-clock time, so a peak line behaves the same on a 60 Hz screen and a 144 Hz one. Both are settings rather than constants, because the Peak/RMS block lets somebody choose them, and "off" and "forever" both have to mean something.
- **Idle is not silence.** A session that is not running and a session playing nothing look completely different: silence is a meter at the bottom, idle is a meter switched off. A person glancing at the window has to be able to tell which without reading anything.
- **The RMS bar is drawn over the peak bar**, so only the tip above it shows in the peak's colour. The peak is always the taller of the two, so drawn the other way round it hides the RMS entirely, which every meter once did.
- **A Peak/RMS tile is bar, scale, bar**: a narrow bar a side with the four marks between them, placed by the same curve as the bars, in the live colour with a paler tip. The reading is in the face's tooltip rather than written under it. Panels and other faces keep their bars side by side.
- **A Peak/RMS block's settings are almost all meter**: bar, scale, bar at full height, with a clip box above each side and its name under it, anything above −6 dBFS red and a white hold line; then the tray and the hold. The numbers are each side's tooltip and accessible description. A block's own settings may ask the card for a width (`panelWidth`) and to leave out the presets row (`wantsPresets: false`); this one asks for both.
- **A clip light can be put out by clicking it.** A latch nobody can clear is a light that is on for the rest of the session and stops meaning anything.

## Errors

- **The engine never produces user-visible text.** It reports `{code, args}`:
  - the code is a dotted identifier, `<area>.<camelCaseName>`, for example `session.corruptFile`, `routing.feedbackLoop` or `device.disconnected`
  - the arguments are a JSON object of named values
- **The GUI translates.** One table maps every code to a translated message, and a unit test fails if a code has no message. A second table does the same for the `reason` an action was refused (`NodeRefused`, `blockNotFound`), which is the engine's own vocabulary and would otherwise be shown to a reader as it stands. A reason with no entry is shown as it came: half a sentence somebody can act on beats a sentence that says nothing.
- **Two places, by what the error is about.** `rb::ui::ErrorSurface` sends an error that names a block to a badge on that block's tile, where the thing that went wrong is, and everything else to an inline banner across the top of the canvas. **The audio system being away outranks all of it**: every other failure while it is missing is a consequence of that one, so the banner says that instead, and carries the Retry.
- **A session that could not be opened is named, and is not forgotten when another comes to the front**. The engine can only give the id it was asked for, since the file with the name in it is what has gone; the window writes down the name of every open session beside its id in the state file, so a restore that cannot put one back says "couldn't find the session “Podcast”" rather than offering the id as a name. Errors about opening are about no session in particular, so they are not cleared with the rest when the session in front changes, which a restore does as it ends, and which used to decide, by whichever answer came first, whether the report was seen at all. The restore then writes down only what did open, so the next start does not ask again.
- **Notices are news that is not an error**: a device a running session uses went or came back (`device.lost`, `device.returned`), an application it captures stopped playing or started again (`capture.lost`, `capture.regained`). They travel like errors, `notice(code, args)` with codes in `engine/core/noticecodes.h`, and hold no words. The runtime finds them by comparing each new plan of a running session with the last one (`planNotices()`): only a block whose match is unchanged counts, so a choice is never news, and an application is "regained" only after it was "lost".
- **Desktop notifications** are the few errors and notices worth one (a recording finished, a device gone, an application quiet or back, a plugin stopped, a disk nearly full, a feedback loop refused), each an event of `notify/reverblabr.notifyrc`, which is what System Settings → Notifications lists. `rb::notify::NotificationPolicy` decides and holds the words, for the window and the daemon alike:
  - a device back within 3 s, or an application quiet for under 5 s, was never lost;
  - the same event about the same block is said once a minute at most.
- **Who says it.** The window sends through KNotifications and holds the bus name `io.github.reverblabr.Notifier` while it does, queued so any number of windows can. The daemon, which has no KDE Frameworks, sends straight to `org.freedesktop.Notifications`, and only while nobody holds that name, so a person hears each thing once whether a window is open or not; it honours the `Action=` a person set in System Settings itself. A finished recording's Open and Show in Folder are KIO's in the window and `xdg-open` and `FileManager1` in the daemon.
- **The system tray** shows the same news without a window. `rb::ui::TrayState` follows the engine: how many sessions run, which Recorders write a file (paused is not recording), and, through a NotificationPolicy of its own, what went wrong that nobody has seen. `rb::ui::TrayIcon`, a KStatusNotifierItem made only in `main()`, shows it: Passive while nothing runs, Active while something does, NeedsAttention (the `dialog-warning` icon) until the popover that says what happened has been closed, or for as long as a session is in error, and a `media-record` overlay while recording.
  - **A left click opens a popover**, a small window of its own (`TrayPopover.qml`) with every saved session, its Run/Stop and its level, and the Peak/RMS and VU meters marked "Show in system tray"; a meter's click brings its session forward. **A middle click shows or hides the main window**, and the icon's menu has Show Reverblabr and All Sessions… above the standard Quit. Wayland tells a tray icon nothing about where it sits, so the popover is placed by the compositor and closes when it loses the focus; the activation token the tray hands over with a click goes to `KWindowSystem::setCurrentXdgActivationToken()` so the window it opens may come forward.
  - **With a tray, closing the main window hides it** and the application goes on in the tray (`QApplication::setQuitOnLastWindowClosed(false)`), its sessions running, in-process or in the daemon alike; Quit in the icon's menu ends it, which stops in-process sessions and leaves the daemon's running. **With no tray** (no `org.kde.StatusNotifierWatcher`, or one with no host registered), closing ends the application as before, and a tray that goes away while the window is hidden brings the window back, so there is always a way to it.
  - **A test never makes the icon**: the window's QML sees TrayState alone, and the icon's own test (`bus.tray`) runs on a private bus against a watcher of its own, in a process of its own, since KStatusNotifierItem waits for the watcher's answer to its first question.
- **Global shortcuts** are KGlobalAccel actions, so they are in System Settings → Shortcuts under Reverblabr and work while the window is in the background or hidden in the tray. `rb::ui::GlobalShortcuts` decides what they are and what each does; `rb::ui::GlobalShortcutRegistry`, made only in `main()` like the tray icon, registers them and passes presses back.
  - **One action per saved session**, `session.<id>` ("Run or stop “name”"), taken from the Sessions window's own list (`SessionOverview`), whose Run opens a session only on disk before starting it. The id never changes, so a key follows its session through reorders and renames. A renamed session's action is registered again under the same id: the old QAction goes first, which KGlobalAccel takes as inactive and keeps the key for, and the new one loads it back. A session gone from the list is forgotten, key and all (`removeAllShortcuts`), except when the list comes back empty, which is as likely a sessions folder that could not be read.
  - **The fixed actions**: `window.show`, `inputSwitch.a`/`.b`, `timeShift.pause`/`.back`/`.forward`/`.live` and `recorder.split`. The block actions act on the front session (`SessionModel`'s, the window's current tab) and on every block of that kind in it, through `ShortcutTargets.qml`, which does what each block's own controls do: the Time Shift's through `TimeShiftState`, from where the running block says its head is; a Recorder's split only while it records.
  - **No default keys.** Any key chosen for everyone clashes with something on somebody's desktop; the actions are there, unbound, from the first start.
  - **A test never registers anything**: the window's QML sees GlobalShortcuts alone, and the registry's own test (`bus.shortcuts`) runs on a private bus against a kglobalaccel of its own, in a process of its own, which also plays the person pressing a key and setting one in System Settings.
- **Log messages are for developers.** They are in English and never shown as interface text.
- **Inside C++, errors are values:** `std::expected` or an error code. Our code does not use exceptions for control flow, and they never cross a layer boundary or reach the real-time thread.

## Logging

- Qt logging categories named `reverblabr.<area>`. Debug output is off by default; turn it on with `QT_LOGGING_RULES`, for example `reverblabr.pw.debug=true`.
- A session started from Plasma logs to the systemd journal; a run from a terminal logs to stderr.
- The real-time thread never logs directly. It writes to the real-time logger ring.
- **The last 500 lines are also kept in memory** (`core::LogRing`), by the window and by `reverblabrd`, each for its own process. The handler that was there before still gets every line; the ring is a copy for the diagnostics bundle.

## Diagnostics

The Info tab's **Diagnostics** section, and **Copy Diagnostics** under it, are for bug reports. The window asks the engine with `GetDiagnostics` only while the section is open, every two seconds, and the answer (described in the interface XML, `version` 1) carries:

- the engine's process, its PipeWire versions, and the audio system as `AudioSystemChanged` says it;
- for each open session: whether it runs, its DSP load and peak, late and lost cycles, rate, quantum, and **whether its data loop is real-time**, as the nodes know it once each has run a cycle. A session that is not says so in the section, in the warning colour;
- **when each session was late**: the telemetry sampler records every rise of the node's count of late cycles with the wall-clock time (`core::XrunHistory`, the last 64), and keeps them across a stop and a start;
- our nodes with their properties, their ports, and every link that has one of them at either end, each end named `node:port`: the part of a `pw-dump` that is ours;
- every recording format and whether this system can write it; what the plugin scan found, by format, and what it left out;
- the engine's last log lines.

The window turns it into one block of **English, untranslated** text, the way `reverblabr-ctl --json` is never translated, adding its own log lines when the engine is another process. It takes out the home folder (as `~`), the user name and the machine's name, the last two as whole words. `.github/ISSUE_TEMPLATE/bug.md` asks for it.

## Internationalization

- Every user-visible string goes through KI18n: `i18nc()` with a context marker in C++, and `KI18n.i18nc()` from `org.kde.ki18n` in QML. The panel widget's QML is the exception: Plasma gives each widget its own translation domain through the global `i18nc()`, so it uses that ([ADR-0024](adr/0024-panel-widget.md)). The notifications' words, which the daemon says too, are marked `RB_I18NC(context, text)` in `notify/` and looked up with gettext in the same catalog.
- The engine produces codes, not text (see [Errors](#errors)).
- Stored data is locale-independent; screens format with `QLocale`.
- Version 1.0 ships in English only, but adding a language must need no code changes.
- The details, and the tools that check them, are in [i18n.md](i18n.md).
